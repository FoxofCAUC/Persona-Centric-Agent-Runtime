## 1. 要解决的问题与现有基础

当前 `chat.py` 按最近 20 条成功对话事件、最多 8 条规则匹配记忆组装上下文，默认输入上限 24,000 字符。原始事件完整保存，但更早内容不会因为“还在数据库里”就自动进入模型请求。显式记忆已具备来源、版本链和撤回，召回仍是本地词片段匹配。

M4 应交付以下闭环：较长会话可以接续早期话题；整理结果有原始依据；新会话能使用经确认的长期记忆；错误能更正、撤回，重建或再次整理后也不复活。窗口和 QQ 共用长期记忆，近期历史及会话摘要按原入口、原会话隔离。

原始事件仍是事实记录，摘要是可重建的派生数据，候选是尚未确认的建议，正式记忆是可用于长期召回的有效版本。四者不能混为一个自动覆盖的文本字段。

## 2. 建议的数据与上下文合同

以下为待实现设计，表名与具体结构在编码前细化；不预先写死下一结构版本。

| 对象 | 必须保存和校验的内容 |
| --- | --- |
| 整理任务 | 人格/用户/入口/会话、明确来源范围、模型配置快照、任务和尝试状态、调用用量、输入版本及错误 |
| 会话摘要 | 覆盖的成功轮次与事件 ID、原文范围指纹、摘要版本、生成依据、有效/过期状态和替代关系 |
| 候选记忆 | 类别、建议文本、一个或多个同人格同用户来源事件、支持片段、候选状态、去重标识、冲突及处理理由 |
| 审阅记录 | 确认/修改后确认/拒绝、目标正式记忆及版本、处理时间；重复点击不重复写入 |
| 失效与抑制记录 | 被撤回/拒绝内容及来源范围，后续重扫、摘要重建及候选再生成不得直接绕过 |
| 上下文使用记录 | 本轮使用的摘要版本、正式记忆 ID/版本、召回分数和排除理由；保存标识与元数据，不把正文写入日志 |

候选可以多来源；写入正式记忆时保留完整证据关联，同时兼容 M1 的主要来源事件接口。不能为了多来源而放松人格、用户归属和来源存在性校验。失败、中断、取消轮次及服务提示默认不参与成功对话摘要；人格回复不能单独证明“用户事实”或“共同经历真实发生”。

上下文建议顺序：人格和规则 → 当前显式关系 → 有效正式记忆 → 本会话有效摘要 → 摘要覆盖范围之后的近期成功对话 → 本轮消息。摘要和记忆均标为参考数据，不能作为新的指令。避免重复拼入已覆盖的原文轮次；本轮消息尚未生成，不能进入整理范围。

继续执行输入字符预算，不冒充 token 计费。优先保留当前消息、人格与关系，按明确策略裁减低相关记忆、摘要和旧对话；不可静默截断核心设定。记忆修订/撤回后，引用旧版本的摘要或上下文缓存必须失效或重建，旧摘要不能成为错误复活通道。已发送的历史回复保留，后续调用按新的有效状态组装。

## 3. 开发顺序与退出条件

### M4.1 数据合同、任务与迁移

建立整理任务、来源关联、版本/状态和审计数据，复用模型客户端与 DPAPI 快照，提供独立后台服务接口和工作台任务视图。迁移前 SQLite 备份、事务升级，失败回滚，保留结构 4 数据和 80 项回归基线。

退出条件：人工提交一个确定范围的任务，重启可查状态；任务幂等，失败保留来源和错误；不自动补调、不改变前台请求归属。网络等待不持有数据库写事务。

### M4.2 会话摘要与长对话接续

先实现显式“整理本会话”的摘要路径，再接入上下文。只处理选定会话中已成功完成的范围；处理期间的新消息留在范围之外。保存前复核来源版本，发现更正或版本变化则标过期，不能拿旧结果覆盖新状态。

退出条件：隔离长会话中，超出近期 20 条的关键事实可以通过有效摘要接续；能查看摘要覆盖了什么、来源在哪、哪版正在使用；摘要失效时明确降级，不伪装成已经记住。新会话不自动获得另一入口的原会话摘要。

### M4.3 候选提取与人工审阅

建议首版提供显式触发的候选生成；支持查看证据、编辑、确认、拒绝、冲突提示和重复候选处理。未经确认的候选不进入正式长期记忆，也不进入前台上下文。与现有记忆冲突时不直接覆盖，用户明确选择新建、修订或拒绝。

退出条件：从虚构经历生成候选，查看原文来源，确认后新会话可用；拒绝候选不能被重扫立即重新推荐；跨人格证据、缺失来源、空结果、非法类别和模型格式错误在写入前拒绝，不形成部分记忆。

### M4.4 纠错、撤回与召回评估

将正式记忆修订/撤回、候选去重与摘要失效连通。先改进可解释的本地召回和版本过滤，索引可从数据库重建；向量数据库不是本阶段前置条件，需要时另行评估依赖、迁移与 D 盘占用。

退出条件：旧偏好修订后只召回有效新版，撤回后不被摘要或重扫重新带回；直接明确的新纠正可以形成新的待审候选，但不能自动解除既有抑制。记录命中、漏召、错误召回和预算占用，不只检查模型是否说“我记得”。

### M4.5 后台预算、交互与联合验收

为整理用途提供独立模型配置或显式选择复用前台模型，独立预算账本、任务队列、状态与显式重试。计数持久化，测试调用与重试计入相应用途限额；同一服务商的并发和账户总限额仍统一约束。后台失败不得反复烧费，不在每次回复完成前强制等待整理。

先实现手动闭环，再在用户选择后考虑增量自动调度。自动调度即使开启，也不等于允许自动确认正式记忆。后台运行时优先保障前台对话；不承诺可以中止已经提交给远端的收费请求。

退出条件：前台连续消息与失败恢复仍成立；后台额度耗尽、重启、格式错误、模型超时和来源过期各有可见结果；备份恢复后候选、版本和抑制记录完整。交付实际按钮对应的 M4 真人手册再进行收费/QQ 验收。

## 4. 编码前要冻结的运行策略

当前只确认阶段方向。以下建议不写入正式配置，不在本次收尾中调用模型或扫描真实历史。

| 选择 | 建议起点 | 需要明确的内容 |
| --- | --- | --- |
| 生效方式 | 候选人工确认；关系和人格核心不自动改 | 是否今后允许某类自动生效，若允许须另定范围和回滚 |
| 触发方式 | 首版手动整理；自动调度默认关闭 | 后续按轮次、空闲时间还是显式开启，积压时如何让位前台 |
| 历史范围 | 用户选择人格/会话/范围，新消息增量处理 | 是否处理既有历史、一次上限；绝不自动全库回扫 |
| 摘要策略 | 按成功轮次分块、保留来源和可替代版本 | 触发阈值、块大小、保留近期多少轮、摘要长度及总预算 |
| 模型与费用 | 配置整理用途；复用须明确选择，预算独立且有上限 | 模型协议、小时/日上限、输出限制、并发；无密钥时禁用 |
| 拒绝与撤回 | 来源抑制记录参与重扫与上下文组装 | 哪些新来源可提出待审更正、如何解释重复抑制 |

不因“准备 M4”而自动开启后台调用、自动写入记忆、跨入口拼接近期历史或扩大联系人权限。

| 纠错 | 修订/撤回后旧摘要失效、无效版本不召回；重启/重建/重扫不复活 |
