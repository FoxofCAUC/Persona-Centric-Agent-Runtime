# 开发验证与验收分级原则

日期：2026-10-29。依据用户追加要求，作为全项目开发原则生效；本轮已授权将此原则与M7.5规划一起提交本地和远端。

## 2026-10-31追加：移除固定验收次数上限

用户明确要求“后续移除测试额度；缺失项追加额度”。后续不再以固定测试次数阻断必要缺项复验；先说明缺口、修复或连接恢复依据，再逐笔记录必要调用，不自动盲重试、不循环刷到通过。已经成功的样例不重放，锁定集与质量门不因此放宽。

此规则替代下文“事前固定次数”的未来执行口径，保留历史预算及结果。正常运行额度、获批供应商、模型参数、权限和单调用时限不变；临时不限额仍需finally恢复，第五次连续失败/QQ中断仍暂停保存断点。仅测试次数上限取消，不构成自动提交推送或增加日常调用授权。

## 1. 默认做法

**阶段性或确有必要时才执行全量验收；日常更新、修改和缺陷修复按影响范围做必要局部验证，通过后即可提交。** 不因每次提交、推送、恢复任务、更新文档或更换执行者重复跑全量。局部通过只证明对应范围，不得写为整个阶段已验收。

“全量unittest回归”“真实模型质量对照”“实际工作台/QQ联合验收”“正式迁移恢复”是不同验证活动，分别判断是否需要。运行全量单元测试不自动要求重跑付费/QQ，也不能代替真实平台证据。

## 2. 按影响分级

| 更新类别 | 默认验证 | 何时升级 |
| --- | --- | --- |
| 文档、路线、链接、归档 | 差异/链接/锚点/状态/哈希；不运行模型或服务 | 文档揭示实现矛盾时另建对应修复，不以跑全量掩盖矛盾 |
| 局部逻辑或缺陷修复 | 复现问题及相邻受影响单元/集成；验证回归风险 | 发现共享合同影响或局部无法界定影响时 |
| 界面/配置/桥接的小改动 | 相关逻辑/权限/草稿/异步响应或适配测试；必要界面/平台样例 | 跨入口、状态机或协议兼容广泛变化时 |
| 存储迁移、来源权限、调度/投递/公共上下文变更 | 先定向及受影响回归；迁移须必要隔离副本恢复 | 若改变共享基础合同或局部不足以界定风险，安排一次必要全量；不能每碰一个共享文件就机械全量 |
| 阶段收尾或跨包集成 | 按冻结阶段合同集中执行必要全量及联合门 | 失败后先针对修复补验；只有广泛影响才追加全量 |

## 3. 全量与付费执行前的判断

记录四项即可：变更影响范围、已有可复用证据、此次新增验证项目、为何需要全量或实际调用。阶段合同已经安排的正式全量执行点无需重复征求许可；新增全量必须有具体理由，不能只写“保险起见”。

全量结果若覆盖代码未变且无新风险，继续复用。重复失败先保留现场、定位并定向验证，不一边修一个小问题一边重跑完整套件。修改共享来源/事务/协议等导致原证据不再有效时，不得为了省时省略必要全量。

付费/QQ只测受影响代表性场景，事前固定次数、总额度和停止条件，逐笔留账；不开评分模型或重复旧72次对照来代替可离线验证的问题。既有真实模型授权、第五次连续失败/明确QQ中断停止规则、临时额度恢复及D盘取证继续有效。

## 4. M7.5专用安排与通用原则的关系

M7.5.1–.3只开发与必要定向自检，.1必须有一次真本地Embedding冒烟；不单独全量、正式验收、正式库迁移或整套付费/QQ对照。.4是唯一正式联合验收点，集中离线A/B、一次计划内全量及必要兼容/恢复/代表性真实样例。失败补验遵循本原则，不把“一次计划内全量”解释为失败后禁止必要复测。

此前文档中“专项后全量”的表述按对应阶段的收尾/广泛变更门理解，不再扩张为每次局部修改都必须执行。历史已执行次数与结论原样保留，不据新原则补造通过或删除失败记录。

## 5. 提交与记录

局部变更完成必要验证、无未解决的对应阻断问题后，可在用户已有授权范围内提交/推送；本原则不是对未来所有任务的常设推送授权。提交说明或交接记录实际验证范围、结果、未执行项和原因即可。

阶段验收报告应汇总有效证据，并明确局部验证与正式退出门。若当前只做文档检查，应直接写“未运行工程/付费测试”，不要引用历史427项作为本轮结果。运行库、权重、私人原文、凭据及真实证据继续留D盘。
