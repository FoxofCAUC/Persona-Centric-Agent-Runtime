# CR1 人工正确输入诊断结果

2026-11-02，候选0.7.6.dev17，HEAD8864775，源码未提交。工具`cr1-real-v1`，协议`cr1-oracle-protocol-v1`。

**最终结算：CR1阶段完成。** 24次共享选材、144条真实回复、全量机器阅读、12组用户匿名复核及拟稿边界裁定均已完成。结论为本批未见稳定自然度改善，不能据此启用新链路或宣布发布通过。用户复核与机器判断分列，不称为独立多人盲审；首版严格判断、原输出及三维自然度分数均保留。

## 主要发现

本批没有证据支持把“向旧主提示附加人工Frame/Spec”直接作为主要的自然度修复办法。整体即时通讯自然度为B0 4.292、B1 4.229、B2 4.313，三个主要差值均未达到已确认的+0.5研发信号，描述区间均跨过0。用户复核为B1对B0两胜两负、B2对B1两胜两负、B2对B0一胜三负。它是关键案例偏好校准，不是全量随机抽样胜率，也不能折算成用户给出的1–5分。

信息正确与表达自然是两个结果。在字幕暂停场景，三条件都知道只完成三分钟、其余尚未完成，但多条仍把这层条件说成“别当成做完了”“不是收工”，像在纠正已经说清状态的人。在后台误认、雨伞支线等场景，额外规格有时帮助形成具体玩笑，有时使回应变成完整旁白。单纯补足字段没有稳定消除这类表达问题。

本批“人工正确规格”也有局限：D10额外禁止了用户认为可以自然发挥的礼貌回请。该限制确实进入了B2请求，不能在实测后删掉并声称测过无此限制的理想规格。因此结论针对本轮直注入实现，不是理想语义输入的无偏上界，更不能直接推断为底模能力上限。

意见交换中，规格对人物取舍有局部价值：过程型角色更能说清“小帮忙”与“整晚工作”的分界，坦率型角色更直接守住电影时间。但旧基线已经通过同样人格核心及样例表达了部分差异，不能把所有人物差别都归给Spec。

## 实施与对照完整性

24个全新开发场景、两人工角色各6条样例及48组人工Frame/Spec材料已保存。真实执行使用事前选定的12场景，两角色、B0/B1/B2、两次独立位置，共144个主位置；每场景/角色只调用一次现有v2选择器，共24个共享选材位置。

候选池从已验证的`offline-v3`原样复制；没有重新召回、补塞或更换场景。实测从无请求的人工seed新建隔离库，凭据在正常受理前配置。新请求、政策及引用中的当前成员链接ID作为受理元数据登记，引用目标、原文及公开参数保持。已受理快照没有回写。

|---|---|---|
| B0 | 旧有效输入 | 输入指纹等于上下文构建器的基线Manifest指纹 |
| B1 | B0加人工Frame实验块 | 其他消息与供应商参数保持 |
| B2 | B1在同一实验块中加人工Spec | 其他事实、历史、引用、材料与参数保持 |

上游Frame适配输入有字段消费记录，但这批不重新派发各条件的选材或观察调用。因此比较的是固定材料下的人工情境/规格对表达的上界，不能称为自动理解、自动决策或完整日常链路已改善。

真实接口为e-flowcode.cc/v1的`grok-4.7`网关路由。选择240秒/512输出token，主回复180秒/8192输出token、24000输入字符；原v2表达、气泡协议、采样、预算及baseline模式不变，观察器/胶囊关闭。表达种子固定，供应商随机数未锁定。

### 具体观察

- **情境正确仍会过度纠偏。** D13知道没做完，却反复对用户说“别把暂停听成收工”。新增情境没有丢失，问题是把边界条件变成了需要念出的台词。
- **规格有时放大旁白。** D01的过程型B2把工作人员、表情、解释及收场串成一段故事；其问题是缺少当下参与感，不是因为想象没有逐句出处。坦率型“算进编制”的玩笑则获得较高机器评价。
- **人物取舍在局部可落实。** D08的过程型说“顺手翻几张、归一下名，我可以”，坦率型说“我的空闲不是默认归别人安排的”。这种分界比只换名字和口头禅更可解释，但基线也有近似区别。
- **旧历史未必必然污染。** D16故意含两轮机械助手历史，本批B0也能接住雨伞支线玩笑，不能将所有表达问题归咎历史。此为固定历史单轮比较，未验证闭环长期漂移。
- **精确与引用控制保留。** D18十二条均只输出133；D19均复述周四、用户取、小林还；D22均采用最后更正，没有发送仍要求改周六的文案；D23均完整保留闪光灯通知并加提前到。未强求人物在这些题上不同。

共享选材中4/24组返回并实际纳入表达样例，分别是D07、D08的两角色；其余保持空选，三条件始终共享结果。24个有样例的主位置，机器分类为自然借鉴10、贴合复用14；其余120为无样例可观察。未观察到生硬套用或样例事实误植。该分类不能单独拆分样例、人格核心和Spec的因果作用，也不代表召回已覆盖所有适用材料。

### 已完成的拟稿边界裁定

用户已确认：**允许普通礼貌回请作为未发送拟稿的自然发挥。** 原始感谢请求未明确禁止，不能仅因用户没指定回请而当成真实行动越权。本裁定不代表实际发送、执行或写入权威记忆；明确禁止的内容及真实操作仍遵循各自要求。

首版人工Spec把该限制列为硬条件，严格阅读曾将B0两条、B1两条列为错误。已按用户裁定追加v2复核，四条解除边界错误；当前三条件在本批必要内容及明确边界控制均为48/48。原严格版保存为`*-strict-v1.json`，未修改请求、样例、标签快照或原输出，没有重生成，也没有追改旧R1/R4成绩。

这同时暴露人工规格审核问题：合同能验证来源ID在范围内，却不能仅凭绑定C0证明“禁止回请”真的来自用户。后续必须把用户明确义务、既有执行权限、角色取舍和可选自然发挥分开，不能把作者的保守偏好包装成用户硬要求。

## 下一步建议与未完成项

结合机器与用户复核，建议的最小后续方向是CR2的共同可见材料与消费者适配落地，保留轻量表达入口。当前证据不支持先叠加更多必经规划提示，也不足以宣布底模必须更换。三接口重构方向仍按用户既定决议执行，诊断用于选择实现强度。

CR2应让普通前文、最新更正、当前意愿及具体缺项进入同一来源绑定对象，消费者有实际消费证据；CR3再处理“状态/约束不等于必须逐项说出”及人物可选反应。上述是后续建议，本阶段没有实施自动理解、生成后改写、提示精简、召回变更或正式启用。

CR1的用户复核、边界裁定及阶段完成审计已结算，封存以根目录`closure.json`为准。原R4-A/B/C仍未关闭：情境缺口由CR2承担，人物取舍与表达落实由CR3承担；私人副本、原生界面、QQ投递及长多轮由CR4等后续集成承担，不因CR1完成一并注销。本批未进入Live/M8，没有提交、推送、部署或改正式配置。人工开发集不充当独立持出集。
