# 模型连接超时排查与修复

2026-10-30，接续滚动五秒与自然分条验收。本修复不增加数据库/配置版本，不修改人格文学或入口政策，不提交推送，不自动追加收费调用。

## 已知原因与证据边界

| 记录 | 事实 | 结论 |
| --- | --- | --- |
| 初次三成员合批 | 同一批次、一次主要调用，60.513秒后provider_timeout；冻结timeout=60 | 达到总请求时限，不是每条输入各等待五秒。旧诊断无法区分等待响应头或读取正文，也不能证明供应商是否完成/收费 |
| 技术窗口 | 相同配置一次成功，17.317秒；代码完整 | 接口不是持续不可用，不能据一次成功否定间歇网络/供应商慢响应 |
| 显式复验 | 5.008秒失败，冻结timeout仍60 | 客户端另设connect=min(5,timeout)，与隐含连接截止高度吻合；旧记录缺阶段，无法追溯确定DNS/TCP/TLS具体哪一步 |
| 复验工具错误 | 使用默认Windows编码读取UTF-8调用记录，HTTP前异常；failed attempt存在，但调用记录未追加 | 验收工具问题，零新增实际云端请求；不能把attempt数量直接当付费次数 |

两次旧超时都只记录统一provider_timeout。不得回写旧诊断为已证实的连接错误，也不得声称远端没有收到请求或没有计费。无证据表明滚动缓冲、三成员合并或私有人格内容导致网络超时。

## 修复方案及实现

1. 移除隐藏五秒连接上限。连接与响应共用冻结配置的总时限（当前60秒）；连接最多也受该总时限约束，不变成连接60秒加生成60秒。关闭aiohttp秒级向上取整，保持配置截止语义。
2. 记录请求准备、建立连接、等待响应头、读取正文、解析响应五个阶段。只保存阶段、单调耗时、总预算、请求头是否已发送和响应头是否已收到，不保存地址、密钥、正文、异常文本或私人资料。
3. 连接阶段超时使用provider_connection_timeout；其他超时沿用provider_timeout。工作台明确提示连接故障。诊断通过现有上下文使用记录落账，不改旧Manifest；不新增表。
4. 不自动重试、不改变主要/选择次数和额度。取消继续传播，迟到响应不应用。没有返回usage时仍未知，不能填0证明免费。
5. 本机验收工具显式使用UTF-8，按原稳定批次找回失败请求；错误和诊断分开保存。失败结果不能因空reply而记“无标点通过”。旧文件保留，不能覆盖失败现场。

首次60秒慢响应没有被“已修复网络”掩盖；若后续仍失败，新诊断才能进一步决定是连通性排查、供应商响应排查还是经用户决定调整时限。当前不更换供应商、不提高总时限，也不改付费预算。
