# M3 开发准备：私聊体验与稳定性

修订日期：2026-10-26。状态：M2 已完成；用户已明确 M3 优先响应速度、连续发消息和失败恢复。本文是新的开发计划起点，尚未实现的功能和未确认策略不自动生效。

本文件取代原群聊准备案。旧案保存在 [历史归档](archive/M3-群聊开发准备-已撤出主线.md)，不得继续作为 M3 的实现要求。总体目标和 M4–M6 顺序见 [项目目标与开发路线](项目目标与开发路线.md)。

## 1. 阶段目标与完成效果

将“已经能对话”的 M2 改善为稳定、顺畅、可理解的私聊服务。主要验收三个问题：

1. **慢在哪里可见、可改善**：分别知道本地受理、排队、模型等待和投递用了多久，窗口不会因为状态刷新显得卡住。
2. **连续消息有明确结果**：用户连续说几句话时，不漏接、不串会话、不静默丢弃，不产生看不懂的重复回答。
3. **出错能恢复**：提交超时、提供商失败、QQ 短断线和服务重启后，能分辨请求是否已受理、是否已生成、是否已发出，并安全继续。

保留现有本人 QQ 与工作台两个入口、同一人格和长期记忆；不新增群聊、其他联系人或多参与者授权。不在本阶段引入自动记忆提取、人格自我演化、搜索或主动问候。

## 2. 当前起点与具体缺口

| 已有基础 | 本阶段要补齐 |
| --- | --- |
| 请求、尝试、投递状态已持久化 | 把状态转换成用户可理解的进度，并明确提交结果未知时如何找回原请求 |
| 同人格串行、有界队列 | 明确连续消息、排队超限、取消及两个本人入口争用的规则，不用取消排序掩盖延迟 |
| 模型超时、额度、显式重试 | 区分未受理、已受理未生成、生成失败、生成完成未投递和投递不确定，各自提供正确操作 |
| 窗口读取结果、QQ 完整回复后分段 | 降低不必要刷新延迟；窗口渐进显示与 QQ 最终投递分别处理，不用部分文本冒充完整回复 |
| 单一模型客户端与配置快照 | 优先优化本地流程和调用参数，不靠隐藏增加模型调用或更换人格来“提速” |
| 正常启停和重启中断恢复 | 验证排空、恢复、长时间运行与故障重开，不自动重放历史输入 |
| 主窗口及编辑弹窗回归 | 扩展覆盖等待、取消、长回复、连续输入和失败保留输入，不回退已修复的保存行为 |

当前最近 20 条成功事件和显式记忆继续作为上下文基础。它们的长期能力扩展放在 M4，不与 M3 的消息状态工程同时大改。

## 3. 分步开发流程

### M3.1：状态与耗时基线

- 为请求增加可比较的阶段时间：受理、进入队列、开始模型调用、首段输出（支持时）、生成完成、落盘、开始投递、平台确认。
- 工作台展示排队/生成/等待投递/完成/失败，使用现有持久化请求状态；状态刷新移出慢速服务身份探测路径。
- 诊断信息记录耗时、请求 ID、错误类别、模型配置标识和用量，不记录聊天正文、记忆内容或密钥。
- 在相同模型和输入条件下采集本地模拟基线；真人延迟采集在用户验收阶段执行，不在开发过程中自动产生收费调用。

**退出标准**：能解释一轮耗时分布；慢服务探测不阻塞结果显示；界面受理提示与真实生成完成有明确区别。先完成观测，再设定优化目标。

### M3.2：可靠受理与连续消息

- 窗口保留稳定的客户端请求标识；本机提交超时后先查询原标识，不能直接生成新 ID 再次调用。
- 连续消息逐条保留来源、时间与原始内容。是否合并回复必须是明确规则；被拒绝的消息显示未受理，不能伪装为已排队。
- 队列操作显示目标人格、会话和处理状态；切换人格、新建会话或跨入口时，原请求归属不变。
- 设计排队取消：取消成功的消息不得随后生成/投递。对已经在远端生成的请求，界面必须区分“本地停止等待”和“远端已确认取消”，不承诺一定免计费。
- 所有受理、取消、重试与回复分组都落到持久化状态，而非仅存在于窗口内存。

**退出标准**：同一会话连续输入 3 条消息，每条均能在记录中找到归宿；返回顺序或合并结果符合已确认规则；重复提交相同请求 ID 不增加一次生成。

### M3.3：等待与回复呈现

- 避免每次等待都触发慢进程扫描；有请求时针对该请求更新状态，后台服务健康检查独立运行。
- 若用户选择窗口流式呈现，则增加可替换的流式读取能力，保持现有完整响应路径兼容。不支持流式的模型不能显示虚假的首字速度。
- QQ 首版建议继续完成生成、持久化后分段发送；等待提示单独标记为服务提示，限制频率，不计作人格回复，不作为成功投递证明。
- 长回复分段保持顺序；部分发送失败进入不确定状态，不能从头自动重发。窗口部分文本也不能作为正式成功轮次进入上下文。

**退出标准**：用户能区分等待与回答；长回复可读且无重复；窗口或 QQ 一侧的呈现优化不破坏另一侧的成功状态判定。

### M3.4：失败恢复与稳定性

- 对模型鉴权、限流、网络、格式、超时及本地存储错误给出不同原因和可执行恢复路径。
- 生成已完成但平台尚未发送的回复，应沿原投递状态恢复，不重新调用模型；投递不确定保持显式人工处理边界。
- 显式重试保留原用户事件和尝试历史，使用当前确认的模型配置，继续核对原 Bot/本人目标，不受切换人格影响。
- 模拟应用重开、服务重启、断线重连、队列积压和配置变更；验证原始数据和成功轮次不丢失。
- 为正常备份/恢复及升级提供工作台说明与隔离演练；紧急强停仍是例外，不替代正常恢复。

**退出标准**：用户能从状态判断正确的下一步；恢复不会重复生成、误投或重放历史；原 M2 真人流程继续成立。

### M3.5：联合验收与交付

- 完整运行既有回归，新增消息状态机、队列/合并、取消、超时未知、重启和平台分段用例。
- 提供 `docs/acceptance/M3-真人私聊验收手册.md`，依据最终按钮和交互编写，不提前虚构尚不存在的操作。
- 真人手册分别验证窗口、QQ、连续消息、失败恢复、正常重启及长时间使用，并记录费用、耗时与未执行项。
- 用户通过后形成 M3 收尾，再开始 M4；生产运行配置和验收记录继续保存在 D 盘。

## 4. 实现前需要冻结的交互选择

已确认的是阶段目标，以下细节仍是建议，进入编码前需要确认：

| 选择 | 建议起点 | 必须明确的边界 |
| --- | --- | --- |
| 连续消息回复 | 提供可配置短时间聚合；未开启时保持现有逐条处理 | 聚合等待多久、哪些消息算同组、发送中来新消息如何处理；不跨人格/会话/入口合并 |
| 输入与取消 | 支持查看并取消尚未开始的排队请求；运行中取消单独处理 | 已发生的远端调用不保证免费，取消后不自动补发 |
| 窗口呈现 | 在协议可用时渐进显示，保留非流式兼容 | 部分输出是否展示、如何标失败、完整保存前不能当作成功回复 |
| QQ 等待提示 | 延迟达到阈值后最多一次，默认文案简短 | 阈值、是否启用、如何与人格正文区分；不借机增加一次模型调用 |
| 速度与稳定性门槛 | 同模型、同输入下对比，分别统计队列/模型/投递 | 先测基线再约定指标，不将模型远端耗时算成本地已经解决 |

不能因为本文件讨论了合并、流式或取消，就将其视为已经启用。前台模型默认不自动重试和项目级预算的既有约束继续生效；调整应写入明确的实现合同。

## 5. 验证矩阵与证据

| 类别 | 必须覆盖 |
| --- | --- |
| 正常对话 | 窗口和本人 QQ 连续对话、长回复、切页和关闭重开窗口 |
| 连续消息 | 3 条短消息、超过队列上限、处理中又来消息、切换会话/人格；每条有明确归宿 |
| 重复与未知 | 同 ID 重复提交、提交响应丢失但后台已受理、生成完成但确认丢失 |
| 模型失败 | 鉴权、限流、断网、总超时、无效输出、流式中断（若实施） |
| 投递失败 | 完全未发、部分分段已发、平台确认失败、目标配置切换 |
| 取消与恢复 | 排队取消、运行中取消边界、重启标记中断、不自动调用或误投 |
| 数据兼容 | 原人格/关系/会话/记忆/调用历史保留，迁移备份及回滚，预算重启不清零 |
| 界面 | 高缩放、编辑保存失败保留输入、忙状态、诊断可理解、无正文和凭据入日志 |

延迟至少区分“受理提示”“首段输出”“完整回复”“QQ 发送完成”，不能选其中最好看的一个代表全部体验。模型自然度主观评价与工程成功/失败分别记录。

## 6. 保留与不做

保留 M2 全流程通过的基线和当前正式数据，不重新初始化、不重建人格、不读取真实对话来制作源码样例。
不为群聊增加新身份或授权表，不开放其他联系人；不并入自动记忆、知识搜索、主动发言、语音或图片生成。本次只修订文档，不修改数据库结构、模型配置、服务状态或权限。
