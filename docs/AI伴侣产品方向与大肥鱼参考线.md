## 产品目的与优先级

PCAR的目的是开发一款持续陪伴用户的AI伴侣：有具体人物的反应与取舍，交流自然，能够让用户愿意主动回来、继续相处。目标不缩减为一个正确执行聊天流程的系统，也不自动把“伴侣”限定成新的恋爱、亲密程度或私人设定；具体关系沿用用户的人物设定与意愿。

对话连续性、长期记忆、关系维护、来源记录和故障恢复都是支持这个目的的能力，不是产品目的本身。工程正确性不得替代产品有效性：通过合同、测试、指纹或封存检查，只能证明对应工程范围，不能据此宣称陪伴体验改善，也不能成为无收益模块继续扩建的理由。

开发优先判断用户是否愿意继续聊天、是否像这个人物在参与交流、是否减少客服感与人机感，再判断实现成本、等待与持续运行代价。工程保护放在程序和维护过程承担，不能要求角色在日常发言里逐句举证、复述限制或播报处理策略。

活泼性优先与拟稿自然发挥原则继续有效：允许贴切的想象、联想、心情与生活细节补白，允许未发送熟人拟稿中的普通礼貌回请。明确更正、拒绝、精确任务、真实执行和权威记忆仍据实处理；这些边界不扩大为日常表达的全面保守禁令。详见[表达原则](表达活泼性与验收优先级.md)。

## 已确认的路线变更

- 暂停CR3-A.1剩余21组。当前13/76条件、旧成绩和未完成项保留；传输冒烟通过不触发自动恢复。
- 下一最小方向为可直接试聊的最简PCAR候选，对照现有PCAR；用户采用“两段短聊＋少量匿名对照”。短聊前移，不再等待CR3、CR4或CR5全部建成。
- 增加成熟“大肥鱼”的实际参考线，尽量对齐基本条件，比较真实体验、实现差距及可复用机制；它是额外参照，不替代PCAR自身的前后对照。
- 情境、决策、表达三接口不再是必须全部建成的既定目标。是否保留、删除、合并或新增，由实际交流收益决定；旧[三接口重构战略](PCAR-交流链路重构战略与开发安排.md)改为历史方案。
- 不先做百次多臂实验、大型评分校准、全仓迁移或完整实验平台。已有运行时、装配、记账和验证能力优先复用，只实现支持这次体验比较的必要接线。
- 不恢复旧批成功或未知位置；不把质量差的完整输出替换成重生成结果。没有收益时作出去留决定，不能默认产生下一版提示或合同。

本次落地的是方向及文档，不是新实测已完成或正式启用。主模型、协议、输出与时间限制、重试政策没有因本文自动改变；不新增硬调用额度，不自动恢复此前已移除的测试限制。具体试聊与参考实例条件在施工前列清，涉及未决方向先请用户确认。

## 尽量对齐条件，保留真实实现差异

| 条件 | 对齐或记录方式 |
| --- | --- |
| 人物与关系 | 同一份获批可见身份、事实、关系距离及表达资料，映射到各项目的正常入口；不硬塞PCAR的内部合同给对方 |
| 模型与供应商 | 尽量同模型入口、供应商、路由、传输和公开参数；记录实际响应标识，模型名相同不等于后端权重固定 |
| 生成参数 | 记录推理设置、采样、输出与时间限制、重试及额外生成；无法对齐项单列，不暗改以追求好看结果 |
| 对话材料 | 固定回放使用同一前文、用户输入、更正、引用和初始记忆；真实短聊从相同初始条件出发，随后分叉如实保留 |
| 插件及记忆 | 列明启用插件、预载样例、记忆、联网及后台能力；不混入旧私人聊天或他人群聊样本 |
| 展示与投递 | 同时看模型原答、后处理文本和用户实际看到的内容；完整产品体验与统一展示的正文偏好分开 |
| 资源代价 | 按回合记录物理调用、可见正文首字、完成及展示耗时、已知用量；不把thinking事件当用户首字 |

对齐的是可比较的起点，提示组织、材料消费、后处理和互动机制本身是要研究的差异，不能为了“相同”把它们抹掉。上游原生大肥鱼人设的展示可以另作原生体验参考，但不能与同人设对照合并归因。

无法固定后端或完全对齐不意味着所有体验观察作废；报告明确“当前配置下更喜欢哪一套”与“某个部件造成了多少提升”的不同证据范围。按预定顺序交错回放，保留所有结果，不筛选后端一致的好样本或补跑制造胜出。

## 从体验差距追到可复用部分

先判断差距是否存在、在哪些具体交流中出现。用户阅读和短聊为体验判断主依据，机器负责整理具体出戏句、任务遗漏、违背更正、人物反应和等待情况。不以机器接近满分的均分、问号数、短句率或禁词命中替代用户感受，也不先要求建成大规模金标准。

实现度按“未实现／已有代码未接通／实际运行有效／用户体验认可”分别标记，不能用插件数、模块数或模拟通过率当作成熟度排名。每个能力都要说明它帮助陪伴体验的方式，例如记住某件事是否让后续互动更贴合，而不只是检索命中了正确ID。

当大肥鱼在某种交流中更好时，依次处理：

1. 保存该轮同条件输入、原答与实际展示差异，描述用户偏好，不代用户编造原因。
2. 追查该实现中真正启用的提示段、样例、记忆、调度、模型参数、分条、后处理或额外校对调用。源码里存在不等于这次生效；不能预设优势来自短提示、无JSON、无规则或某个框架。
3. 只选择一个最有希望、接入成本合理的部分，做小范围关闭／替换／加入比较；必要时直接在PCAR候选接入后验证。调用与展示之外的条件尽量保持。
4. 区分“代码阅读提出的猜测”“完整系统更受喜欢”“受控部件对照有改善”“移植到PCAR后仍有改善”。未完成部件验证时不称其有直接提升作用。
5. 每项给出直接复用、适配复用、仅借鉴或不采用四种结论之一，并说明改善点、源版本与文件、PCAR接入位置、实现和维护成本、额外调用/延迟及尚未验证部分。

默认先寻找现成有效实现，避免为了保持自研架构而重造已验证能力。直接复制、修改适配与独立实现按实际成本和许可选择；采用前核对具体文件、依赖与素材许可、保留必要署名，不默认把角色台词、头像、真实语料视为代码许可覆盖。

研究到付费改写器、主动行为或其他新增机制时可以记录其贡献，但不能悄悄加入PCAR。与既有“一次主回复、复杂至多一次辅助、首版无付费改写”等范围有冲突时，给用户可审阅的收益与代价后再决定。

## 下一步交付和停止规则

先处理最小收尾并准备可聊天候选，同时固定首选大肥鱼版本与插件组合；参考线未就绪不阻断PCAR候选的独立准备。用户仍先完成已同意的两段短聊；额外项目的审阅如何安排随具体运行条件确定，不默认把用户工作量扩成三套长会话或大批评分。

短聊用于发现真实问题，少量同前文匿名回放用于比较；具体数量和解释方式在开始前固定。私人角色副本使用已获批可见资料，不复制正式聊天、记忆或隐藏原件；副本及派生正文、匿名片段、截图、索引、缓存和备份在必要审阅后清除、不提交，只留无正文执行与清理状态。

每轮结束必须决定保留、删除或更换假设：候选明显更好则尽快形成可回退个人试用；两者都差则选择一个新变量；仅连接改善记为可靠性成果。大肥鱼更好而PCAR移植无效时保留失败结论，分析依赖条件，不为证明移植正确继续扩建或调到通过。

新改动要回答三件事：改善哪一种具体陪伴体验、如何让用户尽早看到、没改善时如何退出。文档修改做必要差异与链接核查，代码修改做受影响检查；不为本次方向修订新造付费批次、源码封存包或大规模保护哈希任务。

## 仍然有效的边界与历史

正式Shadow、表达/选择器默认v2及当前数据结构保持，现阶段不自动启用、部署或进入Live/M8。工程边界继续保护私人原件、权限、真实行动、费用记录和用户取消，不转化为日常发言的审计任务。原R4、路由、长期多轮和无人值守未完成项保留，但其旧编号不决定新的产品开发顺序。

旧CR与R阶段证据保持只读、旧成绩不追改。用户更正可以另存并说明发生时间，不冒充新的匿名盲审。新方向允许放弃已经投入但没有收益的模块；不要求先补完旧验收再试用新候选。

方向修订本身未修改生产代码、正式数据、配置或私人角色，未发起真实模型调用或QQ收发。用户于2026-11-04另行授权将已完成成果提交本地及远端；该发布不启动后续实现或测试。GitHub线上主页是否更新以远端提交核实为准，本地README修改不能单独表述为远端已生效。
