# M3 真人私聊验收手册

适用版本：0.3.0；日期：2026-10-26。状态：用户已确认真人验收通过，见 [M3 收尾总结](../M3-收尾总结.md)。下文保留为可复用操作手册，末尾未填写表格是空白模板，不代表逐项实测记录；可选项和长稳独立证据未补造。结果和截图保存到 D 盘，不提交 Git。

## 开始前

1. 关闭旧工作台，双击 `启动人格工作台.bat`，确认标题含 M3。
2. 保留现有人格和模型，不清库、不重装。确认 D 盘可用；在 `D:\Persona-Centric Agent Runtime\exports\acceptance` 新建本轮结果 `.md`，复制文末表格。
3. 记录人格名称/ID、模型名、总超时、小时额度、窗口缩放和起止时间。不要记录密钥、访问令牌或带令牌地址。
4. 首页确认人格服务和消息服务运行；QQ 连接页点击“检查连接”，确认 Bot/本人身份和 OneBot。外部程序占用时从原入口正常处理，不能借验收接管或强停。
5. 故障排查点击“备份数据库”“备份加密配置”，记下 D 盘路径。确认迁移前 `backups/before-m3-*.sqlite3` 存在；新建数据库不要求迁移前备份。
6. 模型页“私聊交互”中先保持两个勾选都关闭。保存不调用模型；不要反复点击“测试已保存配置”。

本轮必测预计约 12–16 次请求，失败尝试和显式重试也可能计费并消耗额度。不要为了验收提高既有限额。每条人工检查期限用“前方排队数量 + 1”乘以模型超时，再加 30 秒；连续三条在 60 秒总超时时最多约 210 秒。超过仍无明确状态记失败，先查详情，不重复发送。

## 必测

### T01 窗口回复与耗时

1. 聊天页选人格 A，点击“新建会话”。发送：

```text
M3窗口-01：请只回复“窗口正常”。
```

2. 等待时切到人格与记忆页再切回；查看“请求队列与详情”，选择该请求，点“查看详情”。

通过：消息、人格回复各一份，状态可从排队/生成变为完成；窗口能切页和滚动，队列与模型耗时有测量结果。首段输出在完整回复模式为空，不能拿它作首字速度。记录 request ID 和人工观察的完整回复秒数；服务端耗时与人工秒表口径分别填写。

### T02 窗口连续三条与输入保护

依次发送，前条显示受理即可发下一条，不等回复；输入下一条时观察文字是否被前条受理回调清掉：

```text
M3连续-1：请只回复“第一条已收到”。
M3连续-2：请只回复“第二条已收到”。
M3连续-3：请只回复“第三条已收到”。
```

通过：三个独立用户消息、三个独立结果，按发送顺序处理，不合并、不漏条、不串会话；新输入没有被清空；排队顺位可解释。模型未严格遵守指定短语单独记为模型行为，不把内容偏差与消息丢失混为一谈。记录三个 ID/尝试数，成功各一次调用。

### T03 请求处理中关闭窗口再恢复

发送 `M3重开-01：请写一段约300字的虚构散步日记。`，显示已受理后关闭工作台，再双击打开，恢复当前会话。

通过：原 ID 和会话保留，可看到原进度或完成结果，没有新用户事件或自动重试；原回复只保存一份。关闭工作台不应停止后台服务。若关闭前已经完成，重新试会增加费用，可记录本项只验证已完成恢复，将进行中恢复记未执行。

### T04 切换期间归属固定

在人格 A 发 `M3归属-01：请只回复“这是A的会话”。`，受理后切到已有测试人格 B，再切回 A。没有 B 时可从模板创建独立测试人格并明确切换，不覆盖正式人格。

通过：请求属于原 A/原会话，B 不继承该事件和记忆。切换后输入的新草稿不会被 A 的受理回调清掉。若请求已完成才切换，进行中部分记未执行，离线覆盖另记。

### T05 明确失败、保留消息与手动恢复

1. 先记下原模型接口地址和模型名，保留密钥。
2. 模型页将接口地址暂设为 `http://127.0.0.1:1/v1`，保存；不点击连接测试。
3. 聊天发送 `M3失败-01：恢复后请回复“原消息恢复成功”。`，等待失败，记录 ID/原用户事件 ID/attempt_count。
4. 不点任何重试等待约 15 秒，检查没有新增尝试或人格回复。
5. 恢复原模型地址并保存，聊天点“重试最后失败请求”，只点一次。

通过：失败原因可见，输入事件保留，没有虚构回复，没有自动换模型；显式重试沿同一请求和同一用户事件新增一次尝试，恢复成功。已完成后不重复调用。结束前必须恢复原模型地址；配置修改不应改变已受理请求的快照。

### T06 未确认消息检查

聊天点“找回未确认消息”，故障排查点“QQ 未确认接收”。

通过：查询本身不调用模型；正常情况下空列表允许通过“入口检查”，但回执丢失恢复仍须记录为**自动验证通过、真人故障注入未执行**。实际出现记录时先查看详情：已受理只找回，不重新发送；未查到受理记录才按需显式提交，保持原标识。QQ 提交前确认当前人格及原账号，按钮会提示可能计费。不要用制造断电或直接改数据库来做必测。

### T07 本人 QQ 连续消息

用配置的本人 QQ，以好友私聊给 Bot 连续发送：

```text
M3QQ-1：只回复“QQ第一条”。
M3QQ-2：只回复“QQ第二条”。
M3QQ-3：只回复“QQ第三条”。
```

通过：逐条完整回复，顺序一致，每条只生成一次，没有 AstrBot 另一份普通模型回答。默认没有等待提示，错误提示若出现须明确标为“服务提示”。故障排查“查看 QQ 待处理请求”中检查相应完成和 sent 状态；成功后列表为空是正常现象。窗口近期历史与 QQ 分开，长期记忆仍共享。

### T08 QQ 长回复与后续短消息

先发 `M3QQ长-01：请写一段约700字的虚构旅行日记。`，紧接发 `M3QQ短-02：只回复“下一条”。`。

通过：若长回复超过 450 字符，分段顺序保持，短消息回复在前条所有分段之后，没有交错、从头重发或重复生成。提供商输出过短导致未触发分段时，分段部分记未执行；不要因未出现长文本就标通过。

### T09 正常停止与重启兼容

1. 等待全部请求处理完、QQ 投递完成；首页点“停止服务”，保留 QQ 登录。
2. 再点“启动服务”，核对身份连接；窗口“恢复当前会话”。
3. 发送 `M3重启-01：请只回复“继续成功”。`。

通过：原会话、关系和记忆保留；旧请求没有再次生成/自动补发；新消息成功。若 QQ 被识别为外部占用，从其原入口按正常方式处理，记录实际状态，不以强停掩盖归属问题。

## 可选功能与异常验收

这些功能默认关闭；准备使用时执行对应项。未执行须保留“未验收”标记。

| 项目 | 做法与通过标准 |
| --- | --- |
| O01 排队取消 | 模型页勾选“允许取消尚未开始生成的排队消息”，点“保存私聊设置”。发送较慢请求，受理后再发第二条；“请求队列与详情”选择第二条，确认仍排队再取消。成功后 phase=cancelled、attempt_count=0，不生成不投递。第一条继续完成。运行中请求拒绝此取消；若第二条已开始则记受阻，不要求硬中断。结束恢复原开关。 |
| O02 QQ 等待提示 | 开启“QQ 等待时发送一次服务提示”，阈值设 5 秒并保存；发送超过阈值的测试消息。最多一次等待服务提示，随后人格回复，提示不增加模型调用、不作为成功送达凭证。不够慢则记未触发。结束关闭并保存。 |
| O03 短断线 | 仅通过本项目正常入口停止消息服务，保留人格服务和 QQ；在窗口请求详情观察 QQ 已生成待投递项，再恢复消息服务。已生成的 pending 沿原投递恢复，不新增调用。若无法自然形成此状态，不强行制造；uncertain 不自动重发，先核对 QQ 历史。 |
| O04 30分钟使用 | 正常少量交谈并切页、滚动、重开窗口；记录时间、额度和失败。无界面冻结或重复生成；不把短测试当长稳通过。 |
| O05 缩放 | Windows 100%/125%/150% 下检查聊天、模型交互设置、队列及恢复弹窗，可滚动到所有按钮，无文字遮住关键操作。记录实际执行比例，自动布局测试另计。 |

鉴权、限流、队列超限、回执丢失、重启中断、发送不确定、迁移回滚和 SDK 路由由离线模拟覆盖；本手册不要求用真实费用/真人 QQ 暴力造故障。真实环境若碰到，留下 ID、时间、错误码和恢复结果，不能自动判为已经验证。

## 证据、失败与收尾

- 每项记录时间、请求 ID、人格/会话 ID、尝试数和可观察结果；截图避开隐私、密钥和令牌。服务日志不应出现正文或凭据；不要把真实聊天粘到 Git。
- 失败先停止本项，保留界面提示和状态，恢复模型地址/开关，不连续重试。投递不确定先查 QQ 是否收到，不能通过重新生成来掩盖。
- 测后恢复原配置；保留验收前后备份及结果文件，正常停止或保留服务由用户选择。不使用紧急强停作为常规收尾。
- T01–T09 必测按实际执行分别判定；T06 的真人丢回执故障注入和 T03/T04 的进行中条件不得由入口可用代替。可以给出“核心真人流程通过，未执行项见表”，不能写所有异常和长稳均通过。
