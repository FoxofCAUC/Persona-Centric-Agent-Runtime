# 修补包 5 · 日常启停与消息恢复

桌面无人值守的主场景是白天随时聊天、收起托盘、晚间完全退出，次日打开后继续使用。验收从首次配置完成的隔离实例开始，每项以真实窗口、进程和消息记录达到预期状态结束。A20 和 R04 采用下列工况。需要验证届期、额度或积压年龄时，向对应组件注入时钟，Windows 系统时间保持正常。

## Windows 实际窗口与进程

使用同一数据目录连续启动三个 WebView2 工作台进程。每次均由工作台监督器启动独立的 PCAR 服务子进程。测试专用的模型接收端只监听本机回环地址，用数字标识记录真正收到的 HTTP 请求。前两次完全退出作为模拟关机的边界。

| 日常操作与中断点 | 通过条件及观察 |
| --- | --- |
| 前台发消息，模型已收到请求时收起托盘 | 窗口隐藏期间后台完成回复。点击托盘菜单唤醒后看见原回复，输入框仍保留原草稿。 |
| 模型端口关闭，消息已在本机受理 | 窗口显示消息已保存、等待网络。托盘内中断本机服务后，监督器自行拉起新的服务进程。再次启动工作台唤回已有窗口。 |
| 彻底退出，重新打开原实例，随后恢复模型端口 | 原角色、会话和草稿恢复。等待消息沿原回合取得一份回复，模型端收到一次。 |
| 断网等待时点「停止本轮」 | 原消息标记为已取消。恢复连接及再次启动后，上游收到该消息的次数均为零。 |
| 上游已收到请求，响应在返回前断开 | 原回合记录结果待核，本地完成回复数为零。下一条消息照常完成。 |
| 刚受理、仍在收集输入时退出 | 下一进程继续处理原批次，收到一次回复。最小化后从启动入口唤回同一会话。 |
| 上游在处理时，本机服务突然终止 | 监督器自动恢复服务，原轮保留中断记录，接收端只收到一次。新消息正常完成。 |
| 每次正常退出 | 核对该次控制台身份、退出回执、所属组件均已释放、原服务端口已关闭。数据库完整性通过，外键违规为零。 |

本轮共受理 **9 条消息**。其中 6 条各生成一份本地回复，1 条主动取消，2 条在上游收到后发生中断。接收端实际收到 8 个不同的消息标识，每个一次。测试包含真实本机 TCP 断开、服务进程结束及重建。没有重启 Windows 或调用付费模型。[进程与窗口演练](../../tests/workbench_daily_cycle.py)

另用一份隔离实例强制结束工作台进程，跳过正常退出清理。Windows 释放其所属服务，检查时残留服务为 0。新进程识别出上次异常退出，恢复原草稿和断网等待的原回合。恢复连接后收到该轮回复和下一轮回复，两次请求标识各出现一次。

重复强退定位到一个断点：端口仍关闭、定时重试刚开始时，旧实现已经登记了下一次模型尝试。修复后，已确认未送达的消息先做 TCP 可达性检查。检查不会发送凭据或聊天正文，也不占模型额度。界面唤醒或网络恢复事件可以提前触发检查。真正重新派发前，服务再次核验原会话、接收方、账号和内容依据。

## 记忆与索引

- **C13** 将人物、会话及原生和导入来源的扫描位置写入数据库。一次轮转最多选两个人物，每人最多两个会话。每个来源页读取最多 16 条新位置，另取最多 10 条已登记待办。分开读取候选与校验、提交，按会话释放写事务。空闲或积压达到条件时推进已授权来源，持续有前台消息时也能完成提取和复核。
- **C14** 将批次的明确失败、等待授权、撤回和需要重验等结果同步到来源记录。验证队列已满时保留原批次。已保存回执按原任务复用，已知未发送的连接失败与效果未知分开记录。
- **C15** 旧整理周期按接收方和账号判定变化。超时等运行参数调整可续接尚未派发的任务。同一密钥重新保存后可继续，无法证明为同一账号的新凭据不能自动接管旧任务。需复核的旧周期按人物保存。
- **C16** 人物索引按人物、资料版本及模型指纹合并排队。队列满和临时文件锁会退避，后续维护轮与重新启动均可再次准备。生成结果仍按来源版本校验。[记忆与索引回归](../../tests/test_daily_memory_recovery.py)

## 对账与后续联合验收

分别记录本机受理、上游接收和用户获得回复的情况。用户有意停止单列。可证明尚未发出的消息按退避时间重试，已发出且缺少回执的消息保留待核结果。单轮调用计数、接收方、人物、会话和已撤回来源都要重新核验。

本机隔离证据位于 `tmp/workbench-daily-1795087814170/result.json`。这些用例验证所列中断路径和恢复行为。真实供应商可用率、自然跨夜观测和其他渠道的登录状态按各自取得的证据记录。

按完整用例名去重，409 项定向回归通过。Windows 启停演练单独记录了工作台身份、进程释放、来源会话、接收端请求序列和数据库结果。导入历史窗口另复验精确引用、来源撤回、迟到的受理回执和重新打开后的会话。

在源码根目录使用带 WebView2 依赖的项目解释器运行 `python -m tests.workbench_daily_cycle <新隔离目录>` 可复验三次启停。另选一个新目录，并在命令末尾添加 `--crash-pair` 可复验异常退出。使用 `--crash-in-probe` 可以精确停在重连探测之中，再强退工作台。修复后，两次独立强退复验和一次探测中强退均恢复原消息，检查到的残留服务均为零。
