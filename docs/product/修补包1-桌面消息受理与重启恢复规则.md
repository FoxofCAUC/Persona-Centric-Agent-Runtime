# 修补包 1 · 桌面消息受理与重启恢复规则

**2026-11-19 · 实现与隔离工程回归完成。** 基线为 Windows 工作台源码 `ee79a52`，业务库结构 33。本包处理 C02 已受理的输入批次、C03 已排队回复的派发判定、C04 工作台丢失本机受理回执。用户点一次发送，重启后仍能找回同一条消息。恢复可以继续有凭据的工作，有疑问的一轮要有明确归宿，用户还能继续聊天。[阶段 0 基线与验收矩阵](../acceptance/桌面无人值守-阶段0基线与验收矩阵.md) · [闭环修补方案](桌面连续聊天闭环修补方案与健壮性评估.md)

## 恢复决策

先核对实例、渠道、本地用户、角色、会话和原请求 ID，再判定相应阶段。**本机收到用户输入、上游执行过一次调用、窗口真正显示气泡，是三个独立事实。** v2 为每个已受理的发送意图保留独立回执。多份回执可以共用一个批次和一个回复回合。v1 已受理的输入直接对应原回合。切换角色后仍按原归属对账。

| 已有证据 | 允许的动作 | 必须保留的结果 |
| --- | --- | --- |
| 只有草稿，或发送意图尚未写入本机 | 保留输入。意图持久写入成功后才能提交本机 | 写入失败时在原会话保留可编辑内容和明确状态 |
| 有发送意图，本机是否受理待核 | 只读查询 C04 的两代受理记录。满足下述权威未受理条件时，才能按原 ID 补交本机 | 接回原受理或保留待核。一条意图最多产生一次受理 |
| 已受理，某个必要阶段可证明尚未外发 | 重新核验原用途、来源、接收方和额度后，领取原阶段继续 | 沿用批次、回合、业务执行版本和已消费预算 |
| 阶段已有可信成功回执 | 核对归属、阶段、逻辑/物理尝试、版本和来源，执行剩余本地结算。只有后续独立阶段自身符合派发条件时才可继续外发 | 原结果只入账一次。回复待呈现时交给原有发布者 |
| 已开始或可能外发，未找到可验证的最终结果 | 查询原凭证。仍无法核实时隔离这次物理尝试，结束对无关后继任务的占用 | 显示本轮结果待核，保留已知用量与未知费用。后继合法交流可继续 |
| 已取消、来源撤回、会话不可写、迁移暂停或授权失效 | 停止相关新派发，保留已有受理和审计。等待合法变化或按原业务合同结算 | 迟到回执只归原尝试。已失效资料不可重新取用或呈现 |

执行前及提交结果时都核对权限和所有权。停止或撤回优先约束后续动作，已发生的外部效果仍如实记账。等待项记录原因、下次检查条件、已用预算和受影响范围。登记、查询、领取或释放本地工作都不能产生新的模型费用。

## C02　已受理批次按原顺序恢复

基线的 `IngressService.recover` 将 `collecting` 和 `sealed_waiting_capacity` 一起转为 `interrupted_buffer`。现行 `_seal` 在首次封批时读取模型配置，`_enqueue` 从同一人物的最早批次开始排队。恢复必须在接收新成员或调度之前识别旧批次的原状态。[输入批次](../../persona_runtime/ingress.py#L39) · [受理与唯一约束](../../persona_runtime/schema_m61.py#L31)

| 中断位置 | 恢复规则 |
| --- | --- |
| 受理事务内 | 原始事件、用户事件、受理回执、成员顺序和批次修改一起提交或回滚。成功提交后才能向窗口确认。重复的同 ID 同载荷返回原受理，不增成员，也不延长收集时间。 |
| 收集中 | 新批次受理时持久绑定作用域、策略、角色资料版本和原获准接收方及配置版本引用。重启用原 `deadline_epoch` 重建进程内单调时钟。旧策略同时遵守原 15 秒上限，滚动策略沿最后一次真实输入的 5 秒静默期，无固定总上限。到期就封批，未到期只等余量。时钟回拨时余量最多为原静默期且遵守已有硬上限。仅新受理成员可按原策略续期。 |
| 已封待容量 | 复用 `sealed_at`、封批原因、成员、主模型及辅助模型快照。容量不足时保留原位，到容量释放再按 `first_seq` 推进。正常运行仍按原策略封批取快照。恢复收集中批次时，若原接收方或配置引用已经变化，只能使用可还原且仍获准的原合同，否则等待或隔离该批。 |
| 关联回合前后 | 写事务中按批次 ID 和版本核对已有 `turns.input_batch_id`。已有回合直接接回。首次建回合与批次转 `linked` 同事务提交，提交后才能调度。同一批次最多一个回合，各成员继续保留自己的请求 ID 和原顺序。 |
| 旧中断记录、显式暂停或取消 | 可由封批时间、冻结快照、成员和关联记录确定的旧批次按原阶段处理。缺乏归属、接收方或暂停原因等必要证据时，保留原事件及待核原因。已取消、已迁移隔离或有明确暂停凭证的记录遵守该决定。 |

可恢复的前序保留已有顺序约束。确认隔离后，将该项从阻塞后继的队首、活跃批次数、待处理字符数与退出排空判定中分别处理，保留对账记录。不得通过伪造取消或完成来腾出名额。同一人物后来的合法发送也要验证。[排队、调度和排空计数](../../persona_runtime/ingress.py#L419) · [既有计时合同](../../tests/test_rolling_chat.py)

## C03　按阶段和物理尝试决定能否续办

基线 `ChatEngine.recover` 把排队及执行中的回合统一置为中断。`_run` 在回合仍为 `queued` 时已能进行角色选材、情境观察和上下文准备。普通显式 `retry` 还可能重新读取当前角色、模型与策略，增加 `execution_revision`。系统自动恢复须使用原执行合同。[恢复入口](../../persona_runtime/chat.py#L228) · [准备与派发](../../persona_runtime/chat.py#L518) · [显式重试](../../persona_runtime/chat.py#L779)

1. **记录未派发的依据。** 新受理的桌面 v1 回合、新关联的 v2 回合，在创建事务中登记恢复合同版本和待领取阶段。服务所有者用写事务领取，以实例、回合、原 `execution_revision`、阶段和所有者代次约束并发。首次领取在任何可能外发的准备动作之前。每次实际调用都先持久记录阶段与尝试编号，再出站。领取与外发分开记录，执行期间不跨网络持有数据库写事务。若崩溃落在已记出站、尚未取得运输证据的间隙，按效果未知处置。
2. **覆盖原路线的所有外发。** 逐项核对本轮实际启用的选择器、情境观察、Jev 决策、受管检索、主回复及已启用的表达子任务。沿用各模块的尝试与回执记录，通过原回合和版本关联。上游受理未知、仅有内存任务、超时、租约过期、主回复尝试表为空或界面显示排队，都不能单独证明未外发。父阶段和子阶段有独立凭证，一项成功或未知不能触发整轮重跑。[选择与观察](../../persona_runtime/character_selector.py#L31) · [观察尝试](../../persona_runtime/situation_observation.py#L136) · [场景路由](../../persona_runtime/scene_runtime.py) · [物理尝试审计](../../persona_runtime/generation_retry.py#L165)
3. **按证据恢复原执行。** 确认旧执行者已失去执行权且原阶段确未出站，才允许新执行者用原快照继续。已知终态错误按该阶段原有重试策略和剩余额度处理。已成功者复用原回执。已证明收到但缺少可用正文的回执保留为已收待核。只有指纹或归属无法验证时保留现有证据，原轮结果仍待核。重启不重置物理重试次数，迟到的旧执行者不能发布、再次派发或覆盖新结果。[主回复与物理回执](../../persona_runtime/schema_expression_runtime.py#L12) · [场景发布恢复](../../persona_runtime/scene_publication.py#L107)
4. **按顺序接管。** 启动先判定迁移和服务所有权，再读取持久批次、回合与各模块证据，结算已有回执，最后才调度可领取阶段。普通 v1 的回合没有 `input_batch_id`，也须进入该判定。旧记录能由原合同证明安全时续办，凭证缺失时单轮隔离。查前发言必须实际可见后才能启动原授权检索。回复沿原路径发布，气泡回执与旧轮发布由包 2 承接。[服务启动](../../persona_runtime/server.py#L42) · [已取得回复的恢复](../../persona_runtime/expression_runtime.py#L332)

## C04　丢失受理回执后找回原消息

新版窗口目前将待确认发送保存在页面会话对象内。`LocalClient.submit_input` 已先写加密意图，但支持按草稿内容匹配，并会在把成功结果返回页面前清理日志。现有 v2 查询收到任意 404 便尝试 v1。下列规则同时覆盖窗口重开、后端重启和确认返回途中失联。[窗口发送](../../persona_runtime/workbench_web/persona_import.js#L1330) · [本机客户端](../../persona_runtime/desktop_client.py#L85) · [加密日志与跨进程锁](../../persona_runtime/submissions.py#L13)

1. **用发送动作区分意图。** 每次明确的新发送生成新的请求 ID，即使正文、引用和会话相同。一次点击产生的重入、传输重试与重开恢复沿用原 ID。发往本机前持久写入原实例、角色、会话、发送时的草稿版本、请求 ID 及原载荷，含引用、公开任务和呈现合同。相同 ID 携带不同载荷或作用域时拒绝覆盖并保留证据。
2. **只读对账先行。** 工作台首次连接、重连、重开、回到会话时，由宿主按实例和原范围查询。新服务在同一读事务中核对 v2 成员回执与 v1 原回合，按各自合同比较归属、载荷和可用凭证。每条新意图返回匹配、明确未受理或待核/冲突，并带原请求 ID 和已存在的回执、批次、回合 ID。旧端仍可查询原记录，按原成员或回合对应关系找回匹配项。普通 404、未识别的接口、认证失败、不可达、双账矛盾和数据库回滚导致的缺记录均保留待核。查询不调用发送接口、不切换当前人物。
3. **仅向本机有条件补交。** 新服务必须明确支持同 ID 原子去重，并能确认在同一实例、同一连续业务库中，两代入口均未受理。还须有有效原意图、完整原载荷、可写原会话、仍获准的用途与来源及接收方。服务端在补交事务中复验这些前提，再查两个入口的记录及冲突。如果从只读查询到写入之间另一写者先受理，则接回那份受理。数据库还原、迁移、旧端能力不足或原范围无法验证时，走只读核对。队满等暂时拒绝登记下次唤醒条件和预算，条件恢复后按原 ID 再判定。重复超时进入退避，重开沿用已花预算。
4. **确保能重开再读。** 将匹配回执或 v1 回合与原意图、发送时草稿版本持久关联后，才清理对应待确认记录。跨 SQLite 与加密日志按原 ID 重做本地核对，任一进程中止后都可完成剩余步骤。只清理仍是发送时版本的草稿，即使新草稿文字相同也要保留。窗口在原会话显示同一条消息并更新其状态。已受理但尚无回合 ID 的成员继续显示等待合批。

### 存储与回退

优先使用结构 33 内能与受理、关联及领取同事务提交的版本化恢复元数据。每项记录原对象、归属、版本、阶段、所有者代次、回执引用及剩余预算。原凭据留在现有凭据存储，审计不复制正文或密钥。新版可自动补交的意图使用独立版本的桌面日志，防止旧 Tk 客户端将已结算条目当成待发项。复用现有加密、跨进程文件锁和原子替换机制。旧记录仍走兼容查询，缺少新合同的旧意图不自动补交。

旧程序接管、备份还原或迁移以后，重新核对实例身份、业务库连续性和真实业务进度。原生记录与恢复元数据若不一致，按仍可核验的最新事实处理，过期的“未派发”标记失效。停用自动恢复时先停领取，保全在途凭证。回退须能读出候选新增业务，升级回来不会重新派发。若结构 33 兼容往返无法成立，按总方案转入显式迁移与回退设计，再启用相应路径。[迁移暂停与凭据清理](../../persona_runtime/migration.py#L114) · [结构 33 与回退条件](桌面连续聊天闭环修补方案与健壮性评估.md#七兼容回退与最终签收)

## 工程回归结果

- 核心恢复、工作台与导入、回复与联网三个分组分别通过 105、50、51 项检查。其中 16 项为本包新增用例。最后修改的路径另复核 34 项，结果全部通过。阶段 0 暴露的历史导出和迁移测试已更新版本断言，原数据校验仍执行。[本包专项用例](../../tests/test_desktop_recovery.py)
- 独立子进程在原稿保存后、业务结算前强制退出。后来两个进程接管同一隔离实例，从原凭证结算一次，运输替身累计调用一次。另验待容量批次、同文新发送、已取消任务、效果未知、旧服务以及还原数据库后不得盲目补交。
- 实际 Windows WebView2 窗口提交数字标记，经本机服务得到一份持久受理、一份主回复回执和一条实际可见气泡回执。此次模型端使用本地替身，真实模型调用为 0。
- 空白、旧版公开历史和含 50,000 条导入气泡的副本分别完成旧版读取、新版写入、旧版写入、新版再读。数据库完整性正常，外键违规为 0，原历史和调用账目数量一致。源码与原始日志分开保存，隔离证据目录为本机工作区的 `tmp/recovery-wp1-1795076118723`。
- 扩展回归中的两项旧 QQ 投递用例在冻结基线和本次工作树均返回 `qq_persona_binding_required`。该渠道处于暂停范围。正式桌面 72 小时运行和真实供应商可用性留待联合验收。本包的证据是隔离工程结果。
