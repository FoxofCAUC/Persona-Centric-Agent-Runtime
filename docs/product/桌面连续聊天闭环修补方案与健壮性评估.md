# PCAR 桌面连续聊天闭环修补方案与健壮性评估

**2026-11-19 · 方案待审 · 主线基线 `ee79a52` · 数据库结构 33**

**交付目标**是让用户完成首次配置和授权后，可以持续聊天。遇到服务重启、短暂失联或后台积压，PCAR 自行找回原消息、继续有证据的工作，并在聊天窗口说明进度。可恢复故障的管理介入目标为零。方案覆盖审查中的 20 个断点、4 项长时风险和 9 类边界，并新增全栈自动排障 C21。以下改动和数值是拟议方案，当前评估属于设计预测。[只读审查原表](../acceptance/桌面无人值守前闭环审查.md) · [桌面验收范围](../acceptance/无人值守陪伴-阶段门与验收矩阵.md)

## 一、怎样判定一件事已闭环

以用户按下「发送」为起点。本机受理、上游物理调用和气泡实际呈现是三个不同的事实。例如，本机已收下消息后窗口掉线，重连应直接显示原消息。如果上游已返回，恢复应使用原回执。如果供应商可能已执行而回执失踪，这一轮应有清楚的归宿，后续交流应能继续。

| 故障发生时的事实 | 恢复依据和动作 | 用户最终看到什么 |
| --- | --- | --- |
| 已按发送，本机受理结果待核 | 先持久保存发送意图，按原实例、人物、会话和请求 ID 查询 v2/v1 受理记录。已受理即绑定原回合。新版本只有在权威查询明确未受理、意图仍有效且接收端能按原 ID 原子去重时，才可自动补交到**本机**。无法核实则保留意图并退避查询。 | 一条消息、一个状态。未按发送的草稿始终由用户决定。 |
| 已受理，有完整冻结范围且可证明尚未外发 | 检查取消、迁移、来源撤回、授权版本和额度。按原顺序领取原任务，用事务记录所有者与执行版本，继续至原阶段。 | 原消息继续排队或回应，无须再点一次发送。 |
| 有可验证的上游回执 | 校验请求、阶段、执行版本和来源归属。复用首次回执完成本地解析、发布或记忆写入，重复恢复只产生一次业务效果。 | 已取得的结果继续出现，相应调用只结算一次。 |
| 有外发可能，无法证明结果 | 单独隔离该次物理调用，记录未知效果、未知用量及其归属。可自动查询已有凭证。没有可靠凭证时结束它对无关工作的占用，原轮的未知结果仍可查。 | 告知该轮结果待核，用户可以继续同人物的下一条交流。 |
| 回复已取得，等待实际展示 | 窗口或会话不可见时持久停在待呈现。只有同人物、同会话、同片段的实际显示证据才可推进回执。已确认前缀作为原气泡读回，不新增投递或历史事件。 | 回到聊天后接续可显示的部分，历史反映已确认的内容。 |
| 用户取消、来源撤回、权限变化或主机退出 | 撤销未开始的工作，取消或废止对应租约，迟到回执只按原合同核对。迁移期间停止外发。真实外部阻塞保留原因、下次检查条件和局部影响。 | 用户看到明确结果。只有缺少新的用户决定时，才在相关操作旁请求一次决定。 |

首包要固定四项工程约束。① 本机确认受理前完成持久写入。② 任一可能外发的阶段先落派发证据，进程身份、租约代次和版本共同约束迟到写入。③ 断线、租约超时、列表里暂时没有记录都不能单独证明供应商未执行。④ 有序任务仅在前序已结算、按既有规则被替代或得到可靠隔离后推进，保留已确认上下文。可恢复任务不能靠一律标为失败或未知来通过验收。[受理日志](../../persona_runtime/submissions.py) · [生成调用审计](../../persona_runtime/generation_retry.py) · [场景发布恢复](../../persona_runtime/scene_publication.py)

每个等待状态登记所属请求、等待原因、唤醒事件、下次检查时间、重试预算和最后一次有效进展。等待期间释放可释放的锁和执行槽。预算耗尽后，由可验证的环境变化重新判断能否续办，或以原证据结算并向用户反馈。窗口重开沿用已花费的预算。无人处理、无唤醒条件且继续挡住后续工作的状态，一律视为未闭环。

每个修补包交付正常入口上的实现、针对故障的自动回归、变更前后证据和回退说明。使用现行主线的 WebView2、双人导入与历史接续入口。独立 W5 提交 `ac7e417` 提供草稿、原回执核对、历史分页及安装保护的参考，接入时维持单一聊天渲染器和呈现者。[主线真实工作台](../../persona_runtime/workbench_web/persona_import.js) · [工作台交付路线](工作台接入与Windows交付路线.md)

| 工序 | 责任与交付 | 前置 | 本包放行证据 |
| --- | --- | --- | --- |
| 0　冻结基线 | 运行时与测试负责人固定支持场景、旧记录样本、权限、额度、硬件和观测口径。把故障注入点放在本机受理、派发、保存回执、实际绘制和提交确认之间。 | 方案定案 | 每个断点有可复现工况或源码判据，当前基线与候选可用同一口径比较。 |

| 3　工作台连续使用 | 前端与本机桥接交付自动重连、浏览隔离、加密草稿、增量历史和可读状态。 | 工序 1、2 | 经主线实际窗口完成失联重开、跨角色浏览、精确引用和长会话输入，全程无需打开设置处理普通故障。 |
| 4　前后台调度 | 整理引擎与查找链共同交付维护故障隔离、前台准入、执行租约、配额公平和排空。 | 工序 0，派发语义采用工序 1 | 后台排满、占槽、额度滚动、取消和迟到结果分别通过，前台与后台都取得有效进展。 |

| 6　运行维护与兼容 | 桌面宿主、安装和存储负责人交付巡检容错、备份提交、退出结算、实例锁、依赖准备与本地自动排障。 | 工序 0 后可并行，联调依赖工序 1 的原请求恢复和工序 4 的排空结果 | 故障恢复后服务继续巡检，备份可实际恢复，退出释放全部所属组件。排障模型不可用时仍能完成已知故障的本地修复。 |
| 7　工程联合复核与候选交付 | 汇总 C、R、B 的工程证据，做跨包故障组合、结构 33 副本往返和跨日工程观察。 | 工序 1–6 通过各自门槛，包括 C21 的本地排障 | 逐项签收工程结果，列出实测值、残余风险和 R04 真实观测设计，提交正式桌面 G-AUTO 入场评审。 |

### C21 的排障选型与执行流程

**优先交付本地自动排障，保留工具调用 Agent 的扩展入口。** 本地规则承担常见故障和模型不可用时的恢复。Agent 擅长在多个模块的症状相似、局部检查结果互相矛盾时，选择下一项诊断和已授权的处理步骤。工具操作由本机执行器核对并提交。Agent 可采用本地推理，或在已获专项授权且可用的独立连接上运行。两种部署均使用同一套本机授权和执行检查。

| 选型 | 适合解决的问题 | 对连续聊天的影响 |
| --- | --- | --- |
| 全本地规则 | 本机失联、服务进程退出、已知文件锁、派发回执核对和可重建索引等已知故障。 | 断网可用，结果容易复验。新出现的复杂故障需要补充诊断规则或由维护者处理。 |

#### 从报错到恢复工作台

1. **收取错误和定位。** 各模块上报实例标识、模块、错误码、阶段、请求状态、时间及可用的调用或呈现证据。同一故障重复上报合并。桌面宿主或启动器在服务断开时仍可查询本机修复状态。提交给 Agent 的诊断数据由本机从允许字段重新组装，限于技术定位所需的错误类别和检查结果。原始日志中的任意文本只作本机证据，密钥、私聊、模型输入及完整路径留在本机权限域。
2. **确定动作与进入维修。** 本机优先匹配已有恢复规则。需要 Agent 时，先允许它查询脱敏诊断，再由它选择或组合已注册的修复动作。执行前，本机核实授权的实例、对象归属、版本、前置条件、可重试次数和可恢复路径。同一实例一次只允许一条维修流程，修复编号、所有者和已用预算落盘。诊断和常规退避可以在后台进行。进入实际维修后，弹窗显示「修复中」及当前步骤，暂时禁用工作台的发送、切换人物和会话、设置保存、导入及其他常规操作，保留进度和安全退出。宿主与本机服务共同拒绝冲突写入和新派发，草稿和已受理消息均保留。
3. **执行与复验。** 本机按同一动作编号执行已授权步骤并保存结果，每一步有时限和限次。中途失败或重启时先核对原所有者及动作回执，符合现有证据和版本时可执行已授权的撤销操作。部分作用未知时保持现场并停止后续写入。修复后同时检查整体健康、原触发条件与本次操作结果。验证成功且写入安全后解除工作台锁定。
4. **恢复原请求。** 本机查询原受理记录、授权和所有可能外发阶段的凭证。可证明尚未派发的工作按原 ID、原归属和有效授权续办，已有可核对的回执直接完成本地结算。结果仍未知的物理调用单轮隔离，后续合法交流继续。用户取消、迁移暂停、权限变化和来源撤回按原合同处理。工作台恢复后显示原消息的当前处置和可用操作。
5. **维修失败时结算。** 达到动作或故障预算时停止扩大修复，保存失败位置与最后证据。写入安全时恢复其余工作，并显示仍受影响的范围。写入安全仍待确认时，结束「修复中」等待并切到仅显示状态和安全退出的界面。真正需要用户决定的事项按具体原因提示，维修锁超时只触发核对，旧操作未结算时保持写入保护。

正常关闭可终止新修复动作并接续原排空流程。已进入执行的动作先按其合同结算，重开按已存维修状态继续核对。[宿主状态与关闭](../../persona_runtime/workbench_webview.py#L225) · [原提交查找](../../persona_runtime/desktop_client.py#L85) · [外发证据](../../persona_runtime/generation_retry.py)

1. 随修补包 6 交付本地流程。使用数字标识、既有回执及受控替身验证重复报错合并、网络和模型同时故障、维修中退出或重启、工作台重开，以及未知物理调用零重发。工作台锁定须能从前端与服务两处核对，健康复验后能恢复正常操作。

3. 只读阶段证明有效后，逐项开放低风险且可复验的动作。检查工具参数被篡改、重复提交、过期计划、跨实例、误判和模型失联时的拒绝、退避及恢复。记录经健康复验且故障在观测窗内未复发的修复率、锁定时长及失败结算。权限越界、重复派发和工作台无期限锁定均为零。桌面日常无人值守以本地流程取得稳定性证据，Agent 可用性单独报告。

## 五、怎样实测修复后的健壮性

时延、负载、时长和回复成功率为**建议目标**，硬门沿用现行验收合同。工序 0 固定 Windows 硬件、存储、显示缩放、库规模、并发、模型与配额，登记典型日常输入速率和可持续处理容量，基线与候选使用相同负载。另报达到或超过容量时的表现。供应商耗时与本机调度耗时分别报告，用户从发送到看到回复的总耗时也单独保留。观测超时只影响统计判定，沿用原请求的执行与收费合同。

| 风险 | 建议工况 | 建议放行条件 |
| --- | --- | --- |
| R01　长会话 | 分别使用 1,000 与 10,000 个原生回合，再叠加 50,000 条导入气泡。使用结构标识，重复切换角色、翻页、滚动及输入。冻结同一台 Windows 机器，每档至少计 100 次交互。 | 首屏或切换可读 P95 ≤ 1 秒，本机发送至可见受理 P95 ≤ 500 毫秒。首屏建议最多读取 60 个回合并设字节上限。单次更新量随变更条数增长。旧消息定位、中文组词、精确引用与可见回执全部正确。 |
| R02　后台压力 | 两个人物轮流聊天，含更正和已授权回填。分别让后台先占满队列、前台持续到达、额度耗尽后自然跨窗。记录写锁时长、前台排队、最老合格任务年龄和实际有效覆盖。 | 可用容量与授权范围内，持续有合格积压时，建议每 10 分钟至少推进一批有效覆盖。按人物和来源观察轮转，一个作用域持续饥饿即不通过。停止注入后积压能清空。前台受理 P95 同时满足 R01。真实冲突、未授权和未知调用逐项计数，一律隔离或停用能力不能达标。 |
| R03　组合故障 | 模拟同一次提交间的两次重启、已派发无回执时换人物、部分呈现后入托盘再退出、慢备份期间磁盘暂时不可写，以及重启预算耗尽后的冷却恢复。 | 本机服务已恢复可访问后，窗口建议 30 秒内自动接回。所有可恢复路径管理介入为零，已持久受理的消息在进程崩溃后丢失为零。所有者、回执、预算、外键及备份校验一致。冷却时间另计并给出下次自动尝试时间。 |
| R04　日常启停、恢复和费用 | 在前台聊天、最小化、托盘、全部退出和冷启动之间轮换。在受理后、模型发送前、服务在途、收到回复后分别中断，恢复原会话并发送下一条。以各项完成条件结束测试。真实模型按已批准的材料、用途和预算取证。 | 正常和可恢复场景管理介入为零。分别核对原始受理、实际派发、回复、取消、待核与费用。后台完成的内容在唤醒后可读，已取消和结果未知的调用重复派发为零。 |

**计量口径。** 可用工况在观测前登记，含合法授权、可写存储、可用提供商与可持续负载。同一请求 ID 计一次用户意图，每个物理调用分别计费。有效受理回合的可见回复率以应回复的有效受理为分母，以在约定观察窗内取得所需真实呈现确认的回合为分子。用户主动取消或按产品合同被后续消息替代者单列。失败、未知及到期仍悬挂的回合不能计作成功。全场景表另列全部发送意图、未受理、取消、部分呈现、外部阻塞、积压、已知费用与未知费用，防止排除困难样本后得出虚高结论。

截止时刻逐条对账。每个已受理回合对应一个业务结果，分别记为完成、取消或合法替代、明确失败、效果未知、仍在推进或等待。完整呈现、部分呈现和未呈现另按气泡回执统计。合批中的发送意图数、回合数和物理调用数分别核对，任何计数差额都必须能回查到原事件。管理介入从首次配置完成后开始计数，用户正常发送、主动取消和决定新授权另行记录。

**跨包故障用例。** 在人物 A 的会话提交后丢失本机受理响应并重启服务。窗口自行找回原受理，在查前发言待显示时进入托盘，再浏览人物 B。回到 A 后按真实显示回执放行原检索。让已授权记忆任务在保存回执后中断，重开后观察本地结算和后续召回。逐段核对用户点击、原请求、物理调用和可见片段。另取独立工况把外发结果置为未知，验证该轮隔离、无重复收费派发、下一条合法交流仍能完成。

**硬门。** 已受理数据静默丢失、成功或未知调用被重放、已确认片段重复呈现、错人物或错会话、撤回后继续取材、越权外发、越额派发、虚假显示确认和错误释放其他进程，任一例即退回对应包。可恢复场景要达到有用的业务结果，不能用“已有终态”代替有效回复或有效整理。

**证据交接。** 每项记录基线与候选提交号、场景和版本、注入位置、原始请求与物理尝试的数量、状态转换、耗时、管理介入、费用和结果。工程诊断使用最少的本机元数据，原话、密钥和模型输入按原权限留在实例。工程用例使用数字标识、既有回执和接口替身。真实工况使用作者已批准的材料版本与用途，触发现行停测条件时保存现场。墙钟时长、真实调用和作者体验分别取证。[模型输入与提示词写作总则](../模型输入与提示词写作总则.md) · [正式联合门](../acceptance/无人值守陪伴-阶段门与验收矩阵.md)

## 七、兼容、回退与最终签收

1. **结构 33 先行。** 优先复用受理、尝试、组织合同和发布回执，只为判定新合同补版本化元数据。旧记录按它已有的证据解读。旧程序必须能读新增业务，在崩溃切回、正常排空切回两种情况下都不得重复派发。若附加元数据无法满足这一门槛，改走显式结构迁移、升级前备份及保留新增业务的独立回退方案，重新定案后启用。
2. **逐包可停。** 内部启用控制归版本交付。停用某条新自动路径时先停领取，再结算已有回执、释放本实例租约和保存明确积压。用户既有聊天、授权和资料继续按版本合同读取。正式用户无需为各修补包逐项配开关。
3. **做新旧往返。** 在空实例、结构 33 历史副本及含双人导入的副本上走旧版读取 → 候选写入 → 旧版读取和修订 → 候选再读。比对已受理消息、人物与会话归属、已呈现前缀、记忆及来源版本、授权状态、物理调用账目和退出结果。专测撤回后回退、删除后恢复，确认退出取材的来源和明确删除的内容不会重新进入聊天。原版 Tk 与现行 WebView2 均从正常启动入口运行。[Windows 交付与回退路线](工作台接入与Windows交付路线.md)
4. **工程入场。** 20 个审查断点和 C21 本地自动排障分别登记实现版本、正常入口、恢复路径、回归与回退结果。9 类边界附处置证据，R01–R03 附工程实测，R04 附跨日工程观察和真实观测设计。出现硬门违规、可恢复工作仍需管理按钮或关键积压无归宿，退回责任包。全部工程条件达到后，由作者决定是否启动正式桌面 G-AUTO。
5. **产品全闭环签收。** 正式观察取得 R01–R04 对应的真实窗口、观测条件、成功率、用户介入和费用报告后，逐项回填残余风险。必要场景受外部阻塞或样本不足时，记录已证明的范围与未验证项。只有规定桌面范围全部通过，才能把本方案中的预期健壮性改列为实测结论。
