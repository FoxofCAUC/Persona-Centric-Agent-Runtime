## 1. M6 最小成功场景

创作者为同一个 persona 添加身高、生日、职业和爱好，未知血型留空。用户在 QQ 分四条发送一件事；原文立即落盘，静默窗口结束后形成一个逻辑回合，读取冻结角色版本和相关真实历史，一次主要生成回复一到三段。发送第一二段成功、第三段未知时，界面准确显示已发内容，暂停余段，不把前两段再次发送；用户可明确处置。原有记忆、关系版本和每日预算保持有效。

此场景不要求 Thread、向量数据库、联网搜索、自动情绪或主动问候。角色事实查询和关键词 Lorebook 是 M6 必交，复杂语义召回在 M7 增强。

## 3. 建议的接口升级面

以下为新协议草案，前缀/路径实施时统一决定，不能当作当前可调用接口：

| 操作 | 语义与兼容 |
| --- | --- |
| 新 ingress POST | request_id、入口身份和载荷；立即返回 receipt/batch，尚无 turn 时合法 |
| ingress 查询 GET | 查受理、成员与批次状态；客户端重启先查询，不自动重放 |
| batch seal/cancel POST | expected_revision、operation_id，重复调用同一结果 |
| character read/update/restore | 事实查询与多版本编辑；导入新角色独立操作 |
| reply/parts GET | 逻辑输出及真实投递摘要，不能只返回一个“已完成” |
| part claim/result POST | capability、claim_token、实际发送结果；旧插件不能领取新 part |
| part resolution POST | 显式处置 uncertain，原因、操作者及对后续队列影响 |

当前 `/v1/requests` 旧语义保留在兼容路径。需要变更返回形状时使用能力协商或新版本路径；不能让旧客户端等待一个永远不会出现的 turn。新的 ReceiptJournal 延续 DPAPI、跨进程锁、稳定 ID 和显式重交规则。
