## 1. 目标与当前差距

**[需求]** 角色应拥有丰富的身份、身体/外貌、背景、性格与爱好，能够进行完成度较高的长期角色扮演；同时拥有可独立持续的人格与真实经历。当前 PersonaSpec v1 只有名字、介绍、核心特征、表达、边界和初始背景，不足以管理完整人设。

**[本计划决策]** 在现有 Persona Runtime 上增加 Character System。M6 不改项目名、不改旧身份 UUID，不把“人格”文本全局替换成“人设”。人设是可见形象与角色正典，人格是稳定反应规律，关系/状态是情境层，经历是时间事实。Prompt 仅是这些数据在一次调用中的表现形式。

这里的“人格”是产品和工程抽象，不能从字段/行为表现推断主观意识、真实心理或医学意义人格。角色可以表达不同意见，不能用无依据亲密或操纵式依赖证明“活人感”。

## 2. 组成与生命周期

| 组成 | 内容 | 生命周期与写入 |
| --- | --- | --- |
| Identity | persona_id、展示名、身份类型、别名 | 持久身份；展示名仍以 M5 core 为准 |
| Character Bible | 身体、外貌、生日、角色时间、职业、背景关系、设定事件 | 创作者显式编辑，版本化，不由聊天事实自动覆盖 |
| Personality Core | 核心性格、价值观、原则、认知倾向 | 复用 M5 core，不复制成第二份可编辑 JSON |
| Social Presentation | 对外形象、语气、社交距离、情境表达 | 基础 style 复用 expression；扩展规则独立版本 |
| Lorebook | 设定人物/地点/物品/故事及激活条件 | 按主题检索，有来源和依赖；不是每轮全量上传 |
| Expression Library | 少量情境语言样例与禁忌 | 人工审核首版；之后只产生学习候选 |
| Runtime Experiences | 实际消息、Session/Thread、记忆、关系、状态 | 真实事件来源，独立权限和版本 |

同一完整角色视图由上述权威数据投影组成，不代表要新建一个拥有全部副本的 character 文档。首版新表以 persona_id 为外键；若需外部 character package ID，它只标识包来源，不成为 Runtime 身份主键。

## 3. 字段模式与验证

| 类别 | 建议字段 | 约束与空值 |
| --- | --- | --- |
| 身份扩展 | aliases、species、pronouns、setting_mode | 未定义可为空；species 不默认强制人类 |
| 年龄与时间 | birth_date 或 birthday、fixed_age、age_policy、setting_timezone/calendar | 固定年龄/随现实增长/随剧情增长/未设定；互斥校验，不混算 |
| 身体与外貌 | height_cm、weight_kg、blood_type、hair/eyes、visual_description | 数值带单位，null 表示未知；不能从血型推人格 |
| 社会背景 | occupation、hometown、education、setting_family、affiliations | 标创作者设定；不能自动当成真实世界存在 |
| 兴趣 | likes、dislikes、hobbies、motivation | 区分设定爱好、后来真实对话形成的观点/偏好提议 |
| 角色世界 | world_id、world_description、canon_policy | 与公共现实世界知识域分开 |
| 社交表现 | public_image、context_rules、humor、catchphrase_policy | 不强制每句口癖；不按数值亲密度机械说话 |
| 设定条目 | subject、predicate、value、unit、valid_time、certainty、visibility | 可精确读事实，也能关联多个背景实体 |

字段不强制全部非空。未设血型/体重不能为“完整度”随机填满。身体数值使用正值/可配置范围与物种语境验证，不把普通人类范围当作所有虚构角色的硬真理；明显异常先提示创作者核对。生日只有月日时不计算年龄；现实闰日、时区和虚构日历应有确定规则。

身份核心和 creator-authored 条目允许“未设定”；模型在普通聊天中只能自然承认未知，或显式提出创作候选，不静默落正典。

建议事实包条目（虚构示例，不是现有 schema）：

```json
{
  "path": "appearance.height_cm",
  "value": 162,
  "unit": "cm",
  "origin_type": "creator_setting",
  "epistemic_status": "canon",
  "visibility": "ordinary_conversation",
  "editable_by": "creator",
  "evolvable": false,
  "version": 1
}
```

完整包再包含 schema_version、persona 关联、来源/作者/许可、内容 hash、导入时间及修订链。校验器使用类型/枚举/长度/嵌套深度白名单；不把网页、脚本或可执行模板直接变成配置。

## 4. 四类“过去”必须区分

| 用户问题或内容 | 正确来源 | 错误做法 |
| --- | --- | --- |
| “你小时候住哪里？” | 创作者设定传记；未知则说明未设定 | 从用户城市记忆猜角色出生地 |
| “我们昨天说了什么？” | 真实事件与 Session/Thread | 用角色的虚构童年冒充双方经历 |
| “你以前说你喜欢这本书？” | 若问角色设定查 canon；若问当时发言查原文 | 只根据当前偏好伪造昨天原话 |
| “这本书今年出新版了吗？” | 公共知识及最新来源 | 让虚构世界规则代替现实出版信息 |

至少区分 `creator_setting`、`runtime_observed`、`user_reported`、`external_knowledge`、`model_inference`、`roleplay_scene`。角色扮演场景可以有虚构共同经历，但必须独立场景作用域，不能自动进入现实共同经历记忆。首版维持普通私聊，场景持久化作为以后扩展，不提前实现完整剧情引擎。

Creator 正典和用户普通聊天内容冲突时：角色可说明自己的当前设定，但用户发来的句子不直接修改设定。明确“修改角色身高”为管理编辑时，走审阅/保存接口，不让主聊天模型获得数据库写权限。

## 5. Identity Anchor 与动态设定

常驻 Anchor 包含简短身份、核心边界、重要反应倾向、当前关系概述与必要社交形象，必须可追踪到版本。其预算是硬上限，不能无限追加口癖和背景。

动态部分分三路：

1. **精确字段问答**：按稳定 path/别名查询，如“你多高”→height_cm，优先确定性读取。
2. **设定实体/主题**：按关键词、实体和 Lorebook 关联激活相关条目，必要时 M7 的本地语义检索补充。
3. **混合历史问题**：分别召回设定和真实证据，例如“上周我们怎么评价你喜欢的那本书”，两类来源明确标记，不能混成一条没有 origin 的文本。

首版无需向量即可实现精确字段与关键词激活，不让 M6.0 依赖 M7 全套向量选型。Lorebook 激活含 scope、priority、required_dependencies、max_depth/max_items、预算与排除项；递归展开必须有深度/循环检测。依赖条目装不下时整组降级并记录缺口，不能只注入导致误解的半条背景。

全部候选先过 visibility/来源/版本过滤；相似度只排序不能越权。`creator_only` 条目不因“用户问了”就暴露；外部卡里声称的“公开/管理员”不得改变 Runtime 权限。当前单用户场景也保留数据属性，避免把内部创作备注自动当作角色发言。

## 6. Character Behavior Resolver

它是上下文组织模块，首版使用代码规则、检索和模板，不增加每轮独立 Agent。输入是本批原文/引用、相关角色事实、Personality Core、Social Presentation、关系、有效状态、真实证据和表达样例；输出 BehaviorContext 及 ContextManifest。

处理顺序：先确定正在回应什么和谁，再选择相关设定/真实记忆，然后组织行为倾向和表达。人格稳定表现为不同情境下反应规律一致，不要求每次用相同句式。认真求助时收起玩笑，熟人调侃时可保留个性，明确纠错时承认事实。

约束冲突的程序优先级：运行权限和数据政策→有效创作者正典及用户显式管理修改→核心行为边界→关系/有效状态→情境表达→示例。过去的原始发言仍是“当时说过什么”的证据，不因为当前正典改变就删除或改写。

主模型输出后先做结构校验与确定性事实检查。能结构化识别的身高/生日冲突可阻止或标记输出；普通文本语义一致性无法保证全部由规则判断，因此还需要固定问题集和人工/机器辅助评估。不要宣称一个正则检查可实现零人设漂移，也不要每轮加昂贵审查调用掩盖延迟。

## 7. 版本、编辑与回退

- 扩展资料每次保存携带 expected_character_version 和 operation_id；冲突返回旧/新版本差异，草稿保留。
- 显式修改 core/expression 字段仍调用 M5 接口；组合编辑需在同一业务事务校验多个 expected heads，避免半次保存。
- 编辑同一角色保持 persona_id，导入“新角色”创建新 persona，继承关系/历史必须另有明确操作，不默认复制。
- M6 批次首条受理固定角色快照；人物身高从 162 改 165 后，已受理批次用旧版本完成，新批次用新版本。
- 回退建立新版本并记录 restored_from；不删除历史，不让旧 state 延期，不撤销记忆屏蔽。
- 字段冲突不能由模型“择优合并”静默解决；保留双方版本，交给用户或确定性规则。
- 导出包含 Character 扩展、core/expression 版本关联、schema 与来源；是否携带私人历史为单独选项，默认角色设定包不带私人记忆/聊天/凭据。

## 8. 旧 PersonaSpec 与外部角色卡

迁移时不向旧 PersonaSpec JSON 直接塞新字段，因为当前验证要求字段集合严格相等、format_version=1。新扩展单独保存，旧 CLI 和导出兼容继续验证；若将来发布 v2，先建立显式转换和版本协商。

外部 Character Card V2/V3 是交换格式参考，不是 PCAR 内部权威 schema。导入器至少给出：来源、作者/许可、可映射字段、不能表达的字段、冲突、将创建新身份还是编辑当前身份、是否含世界书/资源/额外指令。首版只处理受限 JSON；PNG/CHARX 资源后置，不能自动执行脚本、联网下载、访问本机任意路径或解压路径穿越。

`system_prompt`、`post_history_instructions`、宏和正则脚本是外部数据；默认不执行、不提升优先级。角色卡不能开群聊、读取别的人格记忆、替换模型端点、提高预算或启用主动发消息。格式兼容不意味着插件兼容。

## 9. 角色演化边界

M6 建版本与提议接口，M8 可产生观察，M10 再评估提交策略。变化分层如下：

| 变化 | 首版处理 |
| --- | --- |
| 姓名、生日、身高、家庭、出身等 canon | 创作者显式修订；自动演化禁止 |
| 稳定价值与身份边界 | 模型只能提出待审提议；默认不自动提交 |
| 表达习惯、可变观点、兴趣倾向 | 多次真实证据形成候选；先审阅 |
| 关系理解 | 有针对对象、证据和时间，不自动增加亲密度 |
| 临时情绪 | 有 TTL 与原因，不沉淀成永久人格，人工状态优先 |
| 共同经历 | 只从真实互动/明确独立虚构场景分别记录 |

提议记录 target_layer/patch/evidence/rationale/expected_versions/policy/status。拒绝和来源撤回进入屏蔽/去重系统，不能下一次总结原样重提；明确新证据可形成新的、可解释的候选，不能覆盖拒绝历史。

## 10. 验收标准

固定角色事实集至少覆盖已设/未设、修改/回退、时间策略、背景人物、角色/用户同名、普通纠错与创作编辑差异。必测：

1. 精确询问已设身高与生日，返回当前/指定版本事实，不随机变更。
2. 未设血型保持未知；不得后台补齐。
3. 用户故意说错角色生日，普通聊天不修改 canon。
