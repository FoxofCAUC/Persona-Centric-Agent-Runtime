后续架构以[PCAR 信息与决策层及 MaiBot 输出链路开发指导](PCAR信息与决策层及MaiBot输出链路开发指导.md)为准。本页沿用发言硬约束及首轮离线验证，纳入新链路的接线和盲审。

## 角色发言的强制分工

| 执行者 | 本轮责任 |
| --- | --- |
| Planner | 确定接哪条真实发言、是否开口、交流动作、原任务状态、角色要表达的立场、答到哪里与是否结束。把事实、立场和语气要求写入可核验的决策回执。 |
| Jev | 确定是否联网及是否需要长文。长文须有本轮明确请求作为依据。联网先满足公开查询授权并沿已有查前可见回执再派发。 |
| 检索、本地召回与证据决策 | 完整落库，核验来源、版本、撤回、同人物与会话范围。为本轮选定使用的证据和必要限定。需要多个来源比较、冲突处理或追问时，由独立决策模型确定回答所用事实及限定。 |
| Replyer | 根据已冻结的决策、获审的角色表达材料和选定证据生成正文。Pro 若担任 Replyer，只收到完成交接后的写作任务。 |
| 发布核验 | 程序校验决策与稿件来源、输出范围和气泡。专项候选在发布前由独立决策模型核对越权选事实、擅自新增代办和助手式语义。作者盲评完整对话决定自然度是否通过。 |

采用 MaiBot 普通私聊的消息唤醒、真实发言目标、局势与事实交接、当轮篇幅及发送后等待。优先复用固定上游版本的实现和本项目已有适配。每个并行分支共享同一获准快照，依赖检索结果的决策在落库后运行。允许额外决策模型带来延时，用实测首泡和完整可见耗时评估。历史 D3 的 3 秒到期回退不能放行无决策的主回复。参考使用的上游提交为 `478f671e64467121fd3e39205c8d3507b5ce0bd6`。[MaiBot 私聊调度](https://github.com/Mai-with-u/MaiBot/blob/478f671e64467121fd3e39205c8d3507b5ce0bd6/src/maisaka/scenes/private/scheduling.py) · [回复工具与发送后等待](https://github.com/Mai-with-u/MaiBot/blob/478f671e64467121fd3e39205c8d3507b5ce0bd6/src/maisaka/builtin_tool/reply.py) · [Replyer 装配](https://github.com/Mai-with-u/MaiBot/blob/478f671e64467121fd3e39205c8d3507b5ce0bd6/src/chat/replyer/retro_prompt.py) · [PCAR 已有复用清单](../PCAR-MaiBot表达改造施工方案.md)

Planner 与 Jev 可先并行。查到资料且事实或限定仍需取舍时，由独立证据决策模型完成取舍；交接齐备后才派发 Replyer。复核结论只作用于发布，失败稿留档并交给决策阶段处理。用户接受因分工增加的延时，专项同时记录每阶段的真实耗时与用量。

### 派发与失败

1. 角色正文和查前发言分别绑定实例、人物、会话、回合、阶段、执行版本、选定目标、材料版本及决策回执。每次物理派发前重新核对授权和请求快照。工具调用、输出路由、事实与表达材料选择均由 Replyer 之外的阶段完成。Replyer 的传输只接受正文输出，程序持有工具和发送权。
2. 缺失、越界、冲突、迟到、撤回授权或无结论的决策均阻断正文派发。运行器可以等待、使用独立决策器处理歧义，或报告这一轮的真实状态。失败、结果未知、重试、重启、查前、查后、旧场景兜底和结构化输出失败都须验证相同边界。已取得或结果未知的物理调用按原回执恢复与记账。
3. 单独审阅 Planner、Jev、选材和 Replyer 的完整输入。必要的禁令约束放入独立的阶段提示，角色卡完整保留作者文字。提示按实际用途和版本审阅后接入。程序在输出之外落实可直接判定的硬限制。[模型输入与提示词写作总则](../模型输入与提示词写作总则.md)

## 长文与气泡

- 75 字符是每条新发角色聊天气泡的硬上限，计入标点、拉丁字母、数字及空白。发布前检查，任何重试、回退、挂起计划、异常分片和恢复路径均沿用上限。已经显示的历史按原回执读取。
- 普通检索问答默认一句一泡，保全回答中的必要事实与限定。完整底稿与出处留在资料入口，本地召回选出当轮证据后由角色说出结论。需要查看更多时由用户打开详情。
- 用户明确要求连续长文且 Jev 判为长文后，正文进入独立的详情视图。聊天区显示限长的角色发言和详情入口。需要完整保留的长引文、代码或链接进入适用的详情视图。详情尚未具备或输出违反普通模式时，保存原稿、记录失败状态，待本轮按有效决策处理。

## 实施与签收

1. 在真实发布边界落地气泡校验，复验晚间三条长稿、标点稀少的文本、已有超限待发计划和超长保护片段。比较可见正文与原回执，避免重排已发送历史。
2. 用已核验的 MaiBot 流程和 PCAR 已有决策、回执、授权、资料和发送组件接成隔离候选。先用接口替身核对串行、并行、成功与失败的所有派发路径。审阅实际新版本的模型输入与用途后进行有限真实验证。
3. 使用同一角色、同一主模型与采样、相同获准历史和实际输入，对照直接角色扮演、MaiBot 普通私聊与专项候选。作者阅读连续交流、查后短答、话题收尾及明确要求长文的完整显示结果。每一次助手式邀约、无请求追加代办、角色主动把闲聊转成接单、擅自作决策或超限气泡均使该候选未通过。对简单角色扮演的连续体验有可辨识退步也不能签收。作者确认后恢复 G-Auto 断点。

### 首轮工程进度

- 桌面普通回复、原生发言的发布与历史读取现按分片记录输出。新分片超过 75 字符时从已生成的原文重新切分，待发旧分片超限时阻断发送。查前单泡也在发送前校验。以晚间三份保存的原稿离线复验，最大气泡分别为 74、75、73 字符，拼回正文逐字一致。
- 用 D3 现有离线运输验证有效决策、无效决策和超时三个分支。有效决策绑定实际发言输入后才进入 Replyer，无效及超时停止派发。该项验证目前覆盖 D3 的目标、动作及任务状态，后续接入完整的联网、长度、证据和发布复核决策。
- Replyer 禁令已形成待审稿。后续需核对各阶段完整装配、真实接收方和用途，由作者签收真实连续体验后切换发言链并恢复 G-Auto。
