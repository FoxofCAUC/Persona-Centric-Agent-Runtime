# E.N5 连续发言客服感根因复核

作者实际阅读两段15轮回复后，指出人物经常把分享接成追问、让用户选择或提供解决方案。这一反馈触及项目对陪伴体验的核心要求。E.N5 记录为表达体验未通过，进入返工。获选的 B 版保留为对照，原有输入、输出和盲审意见继续按原指纹读取。[产品原则](../表达活泼性与验收优先级.md) · [B 版选型决议](E.N4-原v8Pro基线与桌面呈现.md)

## 实际发生了什么

逐条读取两段的30份用户原话、人物正文及其实际入模前文，并核对对应主模型请求。普通主回复账本保存最终消息指纹、分块指纹、历史来源及原生正文指纹。此次从同版此前留存的系统消息原文核对各块边界，再用每轮的真实历史和当前输入恢复整份消息列表。30/30均与该轮最终输入指纹一致，30/30屏上正文与主模型原生正文指纹一致。

| 检查项 | 本批实证 |
| --- | --- |
| 生成路径 | 30次官方 Pro 主回复，v8 即时通讯合同，原生纯文本。结构33理解、选材以及后置表达重写调用数均为0 |
| 检索与呈现 | 30次 Jev 判断均无需联网，未注入网页资料。Tk 显示原生成文本 |
| 固定材料 | 每轮同一份1,948字符系统消息，由1,238字符的人格与表达指导及710字符的人物补充资料组成 |
| 动态人物资料 | 30轮动态事实、设定与例句命中均为0。没有另外注入关系块、行为指引块、长期记忆或摘要；人物核心资料本身含关系描述 |
| 历史 | 近期双方消息按真实角色回流。11轮还加入了19对额外检索到的历史，其中6对仅由旧人物回复的匹配触发 |
| 文本表象 | 21/30份含问号，12/30份使用同一常见的二选一连接词。这些数字只定位形式；是否出现客服感按当轮用途阅读 |

## 原因、放大因素和边界

**问题首先发生在主回复决定怎样接话时。** 已审的 v8 指导允许自然反应和简短收尾，也要求认真任务做好、按对方意愿取舍建议。实际系统消息没有逐轮追问、提供服务的明文要求。人物设定同时强调理工拆解、保持对话有趣，也包含在对方交办正事时确认目标和报告进展的做法。运行器将整份社交习惯作为固定人物锚点，闲聊和求助每轮同样可见，具体何时适用由 Pro 当场解释。这一边界在本批输出中失守：模型往往能写出技术玩笑或熟人称呼，下一句却转去确定需求、接手任务或要求对方决定角色怎么反应。这是对输入与结果的解释；尚无本批逐变量生成对照，无法将全部行为归因于某一个字段或模型训练阶段。[v8 的表达指导](../../persona_runtime/companion_im.py) · [人物锚点装配](../../persona_runtime/character_context.py) · [v8 分支选择](../../persona_runtime/context_m4.py)

**历史会放大这种应答方式。** 第1段第11轮谈模型版本，额外取回了本段第3轮谈午餐的一整对发言。这一对只有角色上一条回复里的普通二字片段匹配。第2段第13轮谈截图，额外取回第7轮的剧情闲聊，匹配同样来自人物回复。该检索按词项命中和排序选取至多三对较早的发言，加在最近两轮之外。模型于是会再次读到自己无关的追问。另一方面，第2段第3轮把角色应该持何态度交给用户选择，当时输入里只有最近两轮。这说明额外召回影响具体位置，最初的服务姿态也能在没有额外召回时出现。[历史选择](../../persona_runtime/context_builders.py)

**隔离环境的向量模型缺失属实。** 原数据目录内有固定版本的本地模型清单，体验实例缺少同一文件，30轮人物混合检索都退回词法路径。为核对其影响，另建临时隔离库，只加载本批获准的同版人物资料，用已安装的本地模型建立热索引并重跑这30条输入的角色资料检索。30轮都走到混合检索，最终人物资料块的内容摘要仍与本批逐轮一致。这个环境差异值得在后续试验记录，本批客服句式不能用它解释。v8 原合同会剔除对话例句，此行为早于 E.N5；没有证据支持据此恢复大量例句。[模型可用性检查](../../persona_runtime/character_embedding.py) · [原生人物资料消费](../../persona_runtime/companion_native.py)

**回放和验收各有一个盲点。** 两段保留了微信原话，双方实时互动改成了固定的一侧摘句。第2段从游戏切换到软件的两条原话在源记录中相隔超过46天，回放中是相邻两轮。模型问出问题后，下一条继续照原稿送入，可能接不住它的追问。这会放大连续问询和跑题，也不能解释平常分享被主动接成额外服务。

E.N3 的36个新场景位置中，33个 B 请求使用了与本批完全相同的系统消息。此前同版已经出现过在用户补充项目信息时主动提出拆方案的回复，也出现过同样材料下自然调侃并直接收住的回复。原 v8 Pro 获22次首选，足以支持当时的相对选型。此前的验收主要汇总相对排序、上一案例特定状态的重复和赞同词开头，缺少按产品原则单独记录“是否把非求助变成服务”的绝对判断。E.N5 首次工程汇报也只指出了联网和资料复用的缺口。旧版采用记录本来就将同类残留冻结，而且当时采用的是 Flash 型号。[历史采用记录](../AI伴侣重构-v8最终采用与人机味修复结项.md) · [本批基线选择](E.N4-原v8Pro基线与桌面呈现.md)

本批已据此进入[专项施工与首批16位盲审](E.N5-人物接话专项修复施工指导.md)。

## 返工优先级

1. 先处理人物对当前发言功能的取舍。用本批已有原话覆盖分享、吐槽、明确求助和话题收尾，同一个候选必须既能停在自己的反应上，也能在用户真正求助时给出必要帮助。选择问题集时保留自然的反问和有必要的技术澄清作为正例。
2. 优先验证两个可区分的因素。第一组只改变既有任务性人物字段的消费范围。第二组保持原版人物材料，只改变弱词命中时额外历史的纳入条件，保留最近真实对话及真正相关的资料。先用相同原文和固定前文比较，再在各版本独立历史中检验是否越聊越像接待。过去单独屏蔽整条情境规则的对照没有取得稳定优势，不能把删字段直接当作结论。[历史字段消费试验](../acceptance/AI伴侣重构-4E3情境规则消费验收手册.md)
3. 恢复体验验收的否决权。除了比较哪份更好，还应能记录该轮所有候选都偏服务口吻。具体观察人物是否表达自己的关注、是否无故让用户定义需求、对方收尾时能否停止，以及正经求助是否接得住。等待、费用和联网覆盖继续按原账目保留。

30轮全文、逐轮评语、实际前文位置和两种检索模式的比对均在私有诊断页，位置由本机状态 `en5_style_audit_page` 定位。本轮复核新增云端生成请求为0，未编写或启用新的模型提示。
